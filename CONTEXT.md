# Gantry

A repo-driven pipeline for staged, gated processes: content is captured once as modules, documents are rendered from that data on demand. See README.md for the engine's own vocabulary (Definition, Stage, Gate, Module, Instance, Artefact).

## Language

### The engine

**Workspace location**: Where an instance's data physically lives, surfaced in the "+ New Workspace" wizard as one axis — **Server-hosted** or **Local** (`docs/adr/0029-local-workspaces-client-filesystem.md`, `docs/adr/0031-server-workspace-directories.md`). A **server-hosted workspace** is one the `gantry serve` box itself has a handle on, and comes in two kinds: an **Azure DevOps workspace** (data in an Azure DevOps repo, reached with the server's PAT; the mode previously called "workspace-backed") and a **server workspace** (data in a directory under the server's own workspaces root, `lib/workspaceDirectory.js`, WI #355/#356/#358) — each holding one or more instances, each carrying its own `workspace.json` (`{ name, description?, kind: "local", createdAt }`). A **local workspace** keeps its data in a folder on the *browser user's* own machine instead, reached through the Chromium-only File System Access API (`showDirectoryPicker()`); the server holds no registry entry for it, the same `workspace.json` shape in the folder is the portable source of truth, and compute still round-trips to stateless `/api/local/*` endpoints. A server workspace directory and a local workspace are deliberately the same on-disk format (`workspace.json` plus instance subdirectories) — the difference is only *who* is holding the folder, server or browser — which is why both use `kind: "local"` in `workspace.json` rather than a third value: a folder can be copied from one to the other unchanged. A separate later feature, **Advanced mode** (#291), builds on this axis and is not covered here. _Avoid_: "workspace-backed" in new text (say "Azure DevOps workspace" / "server workspace" / "local workspace" as precisely as the point requires); "local instance" or "Server instance" (WI #358 retired both — every server-side instance now lives inside a real workspace, Azure DevOps or server-directory, with no bare/unqualified case left); treating a local workspace as something the server knows about (it does not — no `workspaceRegistry.js` / `instanceRegistry.js` entry, no numeric reference)

**Stage advancement**: How an instance moves to its next stage — always explicit, never implicit, and split purely by whether the instance is local or Workspace-backed (`docs/adr/0014-pull-request-stage-approval.md`, superseding ADR-0012's ticketing-mode mechanism). A local instance advances self-serve via "Advance to next stage"; a Workspace-backed instance advances only when its stage's Pull Request merges. In both modes the action is blocked until the current stage's gate has genuinely passed. _Avoid_: treating a passed gate as if it advances anything by itself — a gate passing merely *permits* the explicit action; also avoid per-instance opt-outs from the PR requirement (there are none)

**Stage branch**: A Workspace-backed stage's own Azure DevOps branch, `gantry-workspace/<slug>/<stageId>` — created the moment a stage's first save lands, targeted by every read/write while the stage is open, and stacked on the immediately preceding stage's branch while that one's PR is still unmerged. `main` only ever reflects fully-approved, merged stages. A completed stage has no branch unless re-opened (`docs/adr/0026-reopen-signed-off-stage.md`). _Avoid_: forking each stage's branch fresh from `main`, or creating the branch only at approval time

**Re-open a signed-off stage** (WI265, `docs/adr/0026-reopen-signed-off-stage.md`): A Workspace-backed completed stage — one the instance has advanced past — can be re-opened for late edits via a **Re-open stage** button shown only when free-browsing that completed stage, gated behind the same PAT/permission check as "Request sign-off". Re-opening recreates the stage branch from current `main`, moves the instance's `stage` pointer back to that stage, and records `reopened: { <stageId>: { at, previousStage } }` on `instance.yaml` — prior `pullRequests`/`workItem` records are preserved, not deleted. The re-opened stage then completes through the existing `requestStageApproval`/`checkStageApprovalStatus` machinery; on merge the marker is cleared and the instance re-advances. Re-opening is blocked if any later stage already has a branch or the instance is more than one stage past the target. Audited via a commit on the stage branch and, when linked, a work-item state/comment push. _Avoid_: treating a completed stage's leftover branch as still needing sync (it doesn't exist unless re-opened), silently overwriting prior approval history, or auto-rebasing later in-progress stages

**Instance number** / **Stage number** / **Workspace number** (WI200, docs/adr/0024): short, scoped, sequential integer references layered on top of today's identifiers, used as the canonical URL form — not a replacement for slugs (still the directory name and registry key) or stage ids (still embedded in Stage branch names). Instance numbering restarts at 1 within each workspace; stage numbering follows each instance's own definition order; workspace numbering, having no parent, is one global sequence. A URL naming a workspace but no instance defaults to that workspace's instance 1; one naming an instance but no stage defaults to that instance's stage 1. Old slug/stage-id query params keep working as a fallback. _Avoid_: treating these as global ids (they're per-parent ordinals, "start from 1" only makes sense that way), or as a rename of slugs/stage-ids (both stay as-is; this is a layered lookup, same pattern `workspaceRegistry.js` already uses for workspace UUIDs)

**Request approval** / **Check status**: The Assignee-side pair gating a Workspace-backed stage. Request approval opens that stage's Pull Request into `main` — the actual approval gate — once its gate has passed; Check status explicitly reads the PR's reviewer votes, distinguishing a rejection or changes-requested vote from a merely-still-pending review, and on detecting approval gantry completes (merges) the PR itself, advances the stage pointer, and pushes any linked work item's state. The Owner approves directly in Azure DevOps. Surfaced in the UI as "Request Sign-off" / "Review / Sign-off" (WI197, docs/adr/0023) — see **Request Review** below for the differently-named, differently-behaved concept those labels sit next to. _Avoid_: polling or webhook-based approval detection (explicitly rejected — detection stays manual), adding an approve button inside gantry, or reading the linked work item as gating advancement (it is a tracking surface only; the PR gates)

**Check gate & sync work item**: A second, independent linked-work-item push — distinct from Check status's own automatic push above. Triggered by the *current stage's content gate* passing (module completeness, independent of any Pull Request), it checks the gate and, only on an explicit confirm click, pushes the gate-passed state to the linked work item. Available for any instance with a linked work item, local or Workspace-backed alike (a local instance has only this action; a Workspace-backed instance has both this and Check status, side by side). WI217 folds this in as a second step of the one Check status click for a Workspace-backed instance — first the Check status refresh/approval-detection sequence runs, then (only if that didn't just advance the stage) the gate-check-and-confirm-sync step — while a local instance keeps this as its own, sole, unchanged button. _Avoid_: conflating this confirm-gated, content-gate-driven push with Check status's own unconfirmed, PR-merge-driven push above — they fire on different triggers and keep their separate confirmation postures even once combined into one entry point

**Request Review**: A Workspace-backed stage's informal, non-gating request for feedback (WI197, docs/adr/0023) — distinct from Sign-off (**Request approval** / **Check status** above), which gates stage advancement. Sending a request creates one Azure DevOps work item per reviewer (never a shared item — `AssignedTo` holds one person), related-linked to the stage's own linked work item. A review's status is read from that work item's own native state (New/Active/Closed) via an explicit "Check status" action, never polling. Available at any time during the stage — not gated behind the gate passing, unlike Sign-off. Review and sign-off statuses both surface on the Work item details card, scoped to the currently-viewed stage only. _Avoid_: confusing this reviewer (an informal feedback request, no bearing on advancement) with Sign-off's own required reviewer (the Pull Request's gating vote, #145/ADR-0014) — different people, different mechanisms, different work items; also avoid reading "sign-off" here as the unrelated module-frontmatter `status`/`owner` convention (**Document history and sign-off** below) — that's document-authoring metadata, this is a stage-level action

**"+ New Workspace" wizard**: The landing page's sole creation entry point (`/new-workspace`, `docs/adr/0013-unified-workspace-creation-wizard.md`): pick an existing workspace or register a new one (setting its Owner then, too), then instance Name + Directory (defaulting to the slugified Name) + initial Assignee, then — only for a ticketing-enabled workspace — the parent-work-item link, with Organization/Project pinned read-only from the workspace and id/type as PAT-backed lookups. _Avoid_: calling it the "setup wizard" or "+ New instance" (both removed), or pasting a raw repo URL as the starting point

**User Guide** (WI183, pending): The app's own in-product help page — end-user-facing (creating workspaces, advancing stages, requesting approval), distinct from `README.md`, which stays contributor/dev-facing (repo setup, architecture, the engine's own vocabulary for people extending gantry). Teaches the engine's generic concepts (Definition, Stage, Gate, Module, Instance, Artefact) using the `design` definition as its worked example throughout, not a manual specific to `design` — written so it doesn't need a rewrite the day a second definition is added. Its stage/gate and artefact reference sections read from each stage/artefact's own `purpose` field (docs/adr/0022) rather than duplicating explanatory prose disconnected from the definition; its module/field content stays conceptual with 1-2 worked examples, not an exhaustive per-module catalog. Content lives as markdown files under `docs/user-guide/`, rendered through the app's existing markdown pipeline. Linked from the header on both the landing page and instance pages, to the left of Settings. _Avoid_: duplicating README's contributor-facing text wholesale — the User Guide covers overlapping concepts in end-user language, from scratch, not by copying README's prose; treating it as `design`-specific documentation; an exhaustive module-by-module catalog

**Archive / restore** (WI223): A reversible "set aside" for a Workspace or an Instance, driven from its Settings screen. Archiving sets `archived: true` on the registry entry (`lib/workspaceRegistry.js` / `lib/instanceRegistry.js`) — nothing on disk or in Azure DevOps is deleted — and the item drops out of the default dashboard and API listings; `?archived=1` / `includeArchived` is the explicit opt-in that shows archived items again, each for a per-row Restore that returns it to exactly its prior state. Archiving a workspace does not cascade to its instances and is blocked (409) while it still has any active instance. An archived instance still resolves read-only at its direct URL (the module editor shows it, `GET /api/instance` carries `archived: true`). _Avoid_: treating archive as a soft-delete (there is no delete; restore is always possible and lossless), or expecting a workspace archive to sweep its instances with it (each item is archived on its own)

### The `design` definition

**Business Case Approved**: The gate closing the `shape` stage, whose display title is **SOAP**. Approves the SOAP (Solution on a Page). _Avoid_: "business case gate" (use the full canonical name in artefacts and docs)

**HLD approved at Technical Architecture Committee (TAC)**: The gate closing the `hld-define` stage, whose display title is **High-level Design**. Approves the HLD (High Level Design) paper submitted to TAC. _Avoid_: "design authority gate" — Design Authority is a different, later committee (see below); this gate belongs to TAC.

**Build Readiness Confirmed**: The gate closing the Detailed Design stage. A single shared gate for both the SAD and SSAD artefacts — they are two renderings of one module set, not two independently-gated documents. _Avoid_: "Design authority" as a name for this gate — that phrase was an unresolved placeholder in the source coverage-assessment spreadsheet and has since been superseded by this canonical name.

**Operational Handover completed and submitted to TAC for noting**: The gate closing the Handover stage. Confirms the as-built/Detailed Design documentation has been produced and handed to TAC for noting (not approval).

**ARB (Architecture Review Board)**: The same governance body as TAC (Technical Architecture Committee) — not a separate committee. Older source material (the SAD template) refers to "ARB approval"; treat this as identical to TAC approval. _Avoid_: treating ARB and TAC as two distinct bodies

**Design Authority**: A governance committee distinct from ARB/TAC. Reviews the `sad`/`ssad` artefacts (via the architecture-related modules) before the Build Readiness Confirmed gate is reached. Not itself a gate — tracked via module frontmatter `status`/`owner`, not a stage exit point. _Avoid_: using "Design Authority" as a gate name — it is a review step, not a gate. This role is a stated intent (Chris Barlow, 2026-08-17), not yet corroborated by a charter or terms of reference.

**SOAP (Solution on a Page)**: In this definition, specifically the artefact for the `shape` stage (whose display title is **SOAP**), rendered from `context`, `solution-definition` and `team-and-estimates` — modelled on the real Confluence Epic SOAP structure. A *different* document, the TAC's own "High Level Solution Design" template, is modelled separately as the `hld` artefact — the two are not the same thing despite both sometimes being called "SOAP" informally. _Avoid_: using "SOAP" to mean the TAC HLD paper

**Full SOAP**: A second, heavier `shape`-stage artefact (`soap-full`) alongside `soap` — a fuller variant of the *same* Confluence Epic SOAP family (`reference/current_design_artefacts/JEDI-Full SOAP Template-240826-023808.pdf`), not the TAC/HLD paper. Reuses `soap`'s own modules (`context`, `solution-definition`, `team-and-estimates`) plus the existing `dependencies` module, extended with fields `soap` doesn't require — see docs/adr/0020. Either `soap` or `soap-full` being complete closes Business Case Approved (docs/adr/0019); authoring both is never required. _Avoid_: treating Full SOAP as a replacement for SOAP, or as the same document as HLD

**SAD (Solution Architecture Document) / SSAD (Solution Support Architecture Document)**: Two artefacts at the Build Readiness Confirmed gate, rendered from the *same* shared module data (`architecture`, `integration`, `data`, `nfrs`, `security`, `risks`, `dependencies`, `support-and-operations`) but with distinct, field-accurate `requires` lists in `definitions/design/definition.yaml`. **Corrected 2026-08-27** (docs/adr/0021, implemented WI181): the two artefacts' `requires` were previously byte-identical, which didn't match the real source documents. `SAD Template.docx` (`reference/current_design_artefacts/`) is an extensive, infrastructure/architecture-heavy blank template — Business Architecture View, Technology Architecture View, Deployment View, Data View, Security View, Operating Considerations — running to ~20 major sections. `FV Help Tool SSAD.docx` (one real filled example, not a template — no blank SSAD template exists) has a genuinely different section list (Solution Products, Architectural Risks, Solution Overview: Stakeholders/Domains/URLs/Environments/Security/Release Procedures). SAD and SSAD are still two renderings of one underlying design (SSAD is support-facing framing of the same solution, not a structurally independent document, per docs/adr/0001) — SAD now requires the complete architecture/requirements/security/dependency views plus only a support-handover summary, while SSAD requires full operational readiness plus only the design fields its support-oriented template actually presents. _Avoid_: treating SAD and SSAD as needing entirely independent module sets (they still share underlying design content, per docs/adr/0001) — the fix is per-artefact field-level `requires` filtering, not a structural split

**Gate-passing is per-artefact, not per-stage-module-list**: A gate passes when *at least one* of its gate-matching artefacts has its own `requires` fields complete — not when a stage's full `modules` list is complete (docs/adr/0019). `stage.modules` still drives the union of modules available for authoring, while each artefact's field-level requirements drive its own completeness and the editor's optional artefact filter. _Avoid_: assuming a stage's gate needs every one of its artefacts fully authored — only one needs to be

**Module completeness by gate, not by authorship**: `nfrs`, `risks`, `security` and `dependencies` are each a single module required at two gates (`hld-tac-approved` and `build-ready-checklist`), filled in progressively — not duplicated as separate lightweight/full versions. Where a field's requiredness genuinely differs between the two gates, that's expressed with the module-spec schema's `required-at` key (see README.md "Field requiredness across shared gates"), not by splitting the field or the module. Most `nfrs` and all `security` fields use `required-at: [build-ready-checklist]`; `risks.risk-register` is required at both gates as-is, since only its expected depth — not its requiredness — changes; `dependencies` uses two distinct fields (`dependencies-overview` required-at `hld-tac-approved`, `dependency-list` required-at `build-ready-checklist`) since the overview genuinely isn't the same shape of content as the full list, not two depths of one field. _Avoid_: creating a second module (e.g. `nfrs-detailed`) for the later gate, or treating `required-at` as a place to encode content depth rather than requiredness. A 2026-08-18 audit found `dependencies` had been built as two separate single-gate fields (`proposed-solution.dependencies` and `integration.dependencies`) instead of this pattern — see docs/adr/0003 — watch for other information categories built the same way before assuming a new module/field pair is genuinely distinct content.

**Cost-benefit vs. NFR**: Cost-benefit analysis lives in `proposed-solution` (the `hld-define` stage, whose display title is **High-level Design**), not in `nfrs`. It's a one-off business justification for the HLD decision, not a quality attribute the built solution must keep meeting. _Avoid_: adding cost-benefit content to `nfrs` — that module is for performance/availability/scalability-type requirements only

**Disaster recovery and backup vs. support-and-operations**: RTO/RPO, backup schedule and retention live in the shared `nfrs` module (`disaster-recovery-and-backup`), not in `support-and-operations` — it's a quality attribute of the built solution, not a support-team-specific concern, even though a 2026-08-18 gap review found it via a real SSAD example. _Avoid_: duplicating backup/retention content in `support-and-operations`

**Document history and sign-off**: Revision history and formal sign-off for a module are tracked via the instance module file's frontmatter `status`/`owner` convention and this repo's git history — not a module field. _Avoid_: adding a `sign-off` or `revision-history` field to any module

**Field ("Section" in the UI)**: A labelled markdown block inside a module (e.g. `problem-statement`'s "Current state"), edited directly in the module editor. Users add new ones via Insert → Section — these custom fields are ordinary fields with an optional title. _Avoid_: "Section" in code identifiers, storage, or API names — Section is UI copy only, never a distinct concept from Field

**Environment (UAT, Production, …)**: Content, not a data-model dimension. An instance has no environment axis — one instance describes one initiative, and the environments that initiative will run in are described *inside* its fields (in v2 canonically `support-and-operations.environments-and-domains`, and at SOAP level in the solution overview and diagrams). The bundled `gantry` instance (`workspaces/examples/gantry`, WI #354) is the worked example: one instance, with UAT and Production (Azure Container Apps) as prose and Mermaid diagrams in `solution-definition`. _Avoid_: adding a per-instance environment field, branch or registry key; creating one instance per environment for a single initiative; confusing "environment" with **Stage** (the process axis Gantry does model) or with **Workspace location**

**Asset ("Image" in the UI)**: An uploaded binary referenced from markdown as `![name](asset:<id>)`. "Image" is the UI label for the toolbar action that inserts an asset reference. _Avoid_: renaming stored references to `image:` or treating "Image" as a concept distinct from Asset

**View mode (Markdown / Split / Visual)**: How a module's markdown fields are displayed and edited on the editor screen — one setting for the whole screen. **Markdown** edits the raw text; **Visual** (planned, superseding today's read-only **Rendered**) is a Word/Loop-style editing surface over the same content; **Split** shows both side by side, each live, with edits flowing to the other pane after a short settle rather than keystroke by keystroke. All three are first-class peers — none is an "advanced" escape hatch. Visual mode's bar is content parity with Markdown mode (including Loop-style table basics: type in cells, Tab between them, add/remove rows and columns, align columns) — never features markdown can't store (merged cells, colours). Images insert/delete in place with the *Source* citation staying automatic; a Mermaid diagram shows drawn and is edited as text in a pop-over; Insert → Section/List stay module-level actions outside the editor. Whatever the editing surface, an untouched section of a field must save back unchanged — only the section the author edited may be tidied — because stage content is reviewed as a Pull Request diff. _Avoid_: "Rendered" for the editable mode (reserve "rendered" for read-only output and generated Word/Excel artefacts); treating Visual mode as a way to store anything the markdown file can't
