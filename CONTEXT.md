# Gantry

A repo-driven pipeline for staged, gated processes: content is captured once as modules, documents are rendered from that data on demand. See README.md for the engine's own vocabulary (Definition, Stage, Gate, Module, Instance, Artefact).

## Language

### The engine

**Provider** (`docs/adr/0037-provider-as-a-suite-one-per-workspace.md`; GitLab per `docs/adr/0041-gitlab-as-third-provider.md`; Atlassian per `docs/adr/0042-atlassian-as-fourth-provider.md`): The external *suite* supplying both halves of a remote workspace — the repo holding its instance content and the tracker holding its work items. **Azure DevOps** (Repos + Boards), **GitHub** (repos + Issues) and **GitLab** (Projects + Issues, self-hosted CE/EE or gitlab.com) are the three built; **Atlassian** (Bitbucket Cloud for content, Jira Cloud for work items) is the fourth, in progress — Cloud only, not self-hosted Bitbucket/Jira Server or Data Center, whose repo/project addressing is a genuinely different shape rather than just a different host. Atlassian is the only **split-suite** provider: Bitbucket and Jira are two separately-hosted products under one Atlassian account, unlike the other three suites, which are each one product bundling repo and tracker together — see **Workspace PAT** for what that costs in credentials. A workspace, and a library repo, names exactly one. _Avoid_: "ticketing system" (the field it replaces — a provider supplies the repo too, not just the tracker); naming a provider after only one of its products ("Jira" for the Atlassian suite, since Jira cannot host the repo); treating content store and work items as separately selectable (they are not — see the ADR for why mixed-provider workspaces are impossible by construction); "Bitbucket workspace" for Bitbucket's own org-level container, now that Atlassian is being built — call it a **Bitbucket account** instead (the collision this glossary flagged while Atlassian was still hypothetical is exact, not adjacent, since "workspace" is Bitbucket's own literal term for it); "GitLab workspace" as a compound noun (GitLab's own product ships an unrelated "GitLab Workspaces" cloud-dev-environment feature — say "a workspace on GitLab" or "a GitLab-backed workspace" instead); "project" unqualified when a GitLab or Jira location is in scope — three providers now use "project" for three different things (Azure DevOps's multi-repo container, GitLab's repo-equivalent shown as "Project" but stored as `location.repository`, and Jira's own issue-container "Project" stored as `location.jiraProjectKey`); a Bitbucket Cloud "Project" (an optional grouping label within a Bitbucket account, unrelated to Jira's) is never surfaced in Gantry at all, so it never needs disambiguating

**AI Provider** (v0.13.0, being planned; `docs/adr/0061-ai-providers-belong-to-the-browser.md`): The external AI service — Anthropic, OpenAI, OpenRouter, Ollama, LM Studio, or any OpenAI-compatible endpoint — whose model reads an Instance's source material and interviews the architect to draft module content. Unrelated to **Provider**: an AI Provider hosts no repo and no work items, and a workspace's Provider never supplies its AI. An architect's AI Providers belong to their browser and serve every workspace, unlike a **Workspace PAT**. Every call except a local model on the architect's own computer goes through the server's **AI relay**, which forwards it, never stores or logs the key, and refuses private and loopback addresses unless the operator sets `GANTRY_AI_ALLOW_PRIVATE_URLS`. Always written in full. _Avoid_: bare "provider" for this (that word is the workspace suite); "LLM provider" or "model provider" as synonyms.

**Question card** (v0.13.0, being planned; `docs/adr/0065-the-ai-interview-runs-on-pinned-grilling-and-domain-modeling-skills-with-standard-modules.md`): One multiple-choice question the AI asks the architect in the AI interview — two to four options, the AI's recommendation (one of them), and optionally the **Source document** it rests on. Cards travel as one `ask_architect` tool call (**native**) or, for a model that doesn't use tools, as a fenced `gantry-questions` JSON block in its reply (**text fallback**); Gantry validates both with the same rules and shows a card only once complete. An invalid native card goes back to the model once. Output that doesn't parse is shown as chat. A card has an `id` (so another card can wait on it with `after`), the Field it feeds, and optionally a `kind` (`disagreement`, `missing`, `term` or `decision`) that Gantry uses to order a **Round** and, for the last two, to log the answer as a **Term choice** or offer it as a **Key decision** (#291); Gantry, not the model, adds the "Other" option, and a select Field's card shows exactly the Definition's `options` with no Other (#287). If the model cannot produce cards the interview falls back native → text (a fenced `gantry-questions` block) → plain chat, and the Interview page shows which at kickoff and in its header. _Avoid_: "form" or "survey"; refusing a model for not supporting cards.

**Test connection** (v0.13.0, being planned): The check run on an **AI Provider** from Global Settings, in order: key accepted, model exists, **Question card** mode (the AI Provider's own metadata hint, then an authoritative probe call), and whether the model reads images. The result is stored with the AI Provider and shown as labels; changing its Type, Address or Model marks it untested; an untested one is tested automatically when a session starts.

**Content store**: The Provider capability that reads and writes a workspace's instance and definition files, branches and commits — one of four, alongside pull requests, work items and identity (`docs/adr/0039-provider-capability-interfaces-and-normalized-errors.md`). Named as a role a provider fills, not as a component: a local workspace's content lives in a browser-held folder and a server workspace's in a directory on the serve box or a **Blob container**, with no provider involved at all. _Avoid_: "storage" or "backend" for this (both already mean something else here — `lib/storage.js`'s filesystem seam, and gantry's own server); treating it as a synonym for the repo (the repo is where a *remote* workspace's content store happens to put things)

**Workspace PAT** (`docs/adr/0038-per-workspace-pat-no-global-credential.md`): The Personal Access Token a single workspace authenticates to its **Provider** with, held in the architect's own browser and forwarded per request — or, for the **Gantry MCP server**, held instead in its own **MCP workspace-PAT map** and forwarded the same way. There is no global or default PAT and no fallback — a credential's blast radius is one workspace, which is what keeps an Azure DevOps token from ever being offered to GitHub. An **Atlassian** workspace is the one exception to "one PAT" (not to the blast-radius rule): being a split-suite provider, it holds *two* tokens in that same one workspace slot — a Bitbucket token and a Jira token, each sent only to its own product's API — because the two halves are different Atlassian products with their own separate token systems, not because Gantry's own credential model needed a second axis (`docs/adr/0042-atlassian-as-fourth-provider.md`). A **Library repo** is the exception to the *architect-held* half instead: it authenticates with a server-held environment credential, one per provider — an Atlassian library repo needs only its Bitbucket credential, since a library repo holds definitions and receives Promote PRs but never touches work items, so its Jira half is simply never exercised. `GANTRY_SHARED_WORKSPACE_PATS` (`docs/adr/0047-a-workspace-can-be-shared-by-its-deployment.md`, superseding `docs/adr/0046-boot-time-bootstrap-pats-amend-adr-0038.md`'s narrower, boot-only exception of the same shape) is a second, deliberate exception to "held only in the browser": an opt-in, off-by-default `{workspaceId: pat}` map declaring a workspace *shared* — the deployment itself reads it, for reads only, so any visitor with no credential of their own still sees that workspace's rows. It is used twice: once at boot, to run Provider-backed instance discovery immediately (as `docs/adr/0046` originally scoped it); and again on every later request that carries no credential for that workspace, to build its rows — the point of the rename, since a name that reads like a startup detail must not silently double as "anyone may browse this." Writing never uses it — every mutation still resolves the requesting person's own PAT or does not proceed. _Avoid_: "the user's PAT" or "the server's PAT" as if either were a single thing; treating a missing PAT as a workspace being misconfigured (it just prompts, and the answer lands in that workspace's slot); calling an Atlassian workspace's pair "the PAT" singular once Atlassian ships; treating `GANTRY_SHARED_WORKSPACE_PATS` as a global/default credential the way `docs/adr/0038` forbids for writes (each entry is still scoped to exactly one workspace, and never used for a mutation); describing it as startup-only or discovery-only now that it also serves reads.

**Workspace location**: Where an instance's data physically lives, surfaced in the "+ New Workspace" wizard as one axis — **Server-hosted** or **Local** (`docs/adr/0029-local-workspaces-client-filesystem.md`, `docs/adr/0031-server-workspace-directories.md`). A **server-hosted workspace** is one the `gantry serve` box itself has a handle on, and comes in two kinds: a **remote workspace** (data in a **Provider**'s repo, reached with that workspace's own PAT; called an "Azure DevOps workspace" until GitHub became a second provider, and "workspace-backed" before that) and a **server workspace** (data in a directory under the server's own workspaces root, `lib/workspaceDirectory.js`, WI #355/#356/#358, or, chosen under **Store in**, in a folder of a **Blob container**, `docs/adr/0070-a-server-workspace-can-be-stored-in-an-operator-declared-blob-container.md`) — each holding one or more instances, each carrying its own `workspace.json` (`{ name, description?, kind: "local", createdAt }`). A **local workspace** keeps its data in a folder on the *browser user's* own machine instead, reached through the Chromium-only File System Access API (`showDirectoryPicker()`); the server holds no registry entry for it, the same `workspace.json` shape in the folder is the portable source of truth, and compute still round-trips to stateless `/api/local/*` endpoints. A server workspace directory and a local workspace are deliberately the same on-disk format (`workspace.json` plus instance subdirectories) — the difference is only *who* is holding the folder, server or browser — which is why both use `kind: "local"` in `workspace.json` rather than a third value: a folder can be copied from one to the other unchanged. A separate later feature, **Advanced mode** (#291), builds on this axis and is not covered here. _Avoid_: "workspace-backed" or "Azure DevOps workspace" in new text (say "remote workspace" / "server workspace" / "local workspace" as precisely as the point requires, and name the **Provider** separately when it matters — "a remote workspace on GitHub"); "local instance" or "Server instance" (WI #358 retired both — every server-side instance now lives inside a real workspace, remote or server-directory, with no bare/unqualified case left); "server workspace" for a Provider repo registered with the server (that is a remote workspace; the wizard's labels said otherwise before v0.13.0); treating a local workspace as something the server knows about (it does not — no `workspaceRegistry.js` / `instanceRegistry.js` entry, no numeric reference)

**Blob container** (`docs/adr/0070-a-server-workspace-can-be-stored-in-an-operator-declared-blob-container.md`): An Azure Blob Storage container the operator declares to a deployment by name, URL and credential type, which the "+ New Workspace" wizard offers under **Store in** as a place to keep a new **server workspace** instead of the server's disk. It is offered even with Advanced mode off, as the alternative to a Local workspace. Settings lists each one read-only, with whether it can be reached. Each server workspace stored there is a folder in the same layout as on disk, so a folder copies between disk and container unchanged. The container, not any one server's registry, is the truth about the workspaces it holds, so every server sharing it and every restart sees the same workspaces, Instances and short numbers. Its credential belongs to the deployment, never to an architect: the third server-held credential, after **Library repo** credentials and shared workspace PATs. A server workspace stored in a Blob container still has no commits, PRs or work items. When a container cannot be reached, the workspaces last seen in it are **unavailable**: listed with the reason (never an SDK message), their Instances not openable, and the rest of Gantry unaffected (#269). A folder copied into a container with Azure's tools is found as a new workspace with a new id and new short numbers. _Avoid_: "blob workspace" as if it were a third kind beside remote and server workspaces (it is a server workspace, stored elsewhere); calling it a **Provider** (it has no tracker, PRs or branches); "storage" or "backend" for it (see **Content store**); calling its credential a PAT

**Definition home**: Where a definition lives — the **server library** (the `definitions/` directory packaged with, or configured for, `gantry serve`, plus every **Library repo** below) or a **workspace** (a `definitions/` folder inside a server workspace, remote workspace or local workspace, same on-disk layout as the library). An instance may use any server-library definition or any definition in its own workspace; a definition id is unique across the library and every workspace, so an id always names one definition. _Avoid_: a workspace "shadowing" or overriding a library definition of the same id (refused, not resolved by precedence); treating a workspace definition as reachable from another workspace

**Library repo**: A repo on any **Provider**, listed in Settings (any number), that holds definitions under `definitions/`. Unlike a workspace, it authenticates with a server-held credential rather than the architect's own — one environment PAT per provider (`docs/adr/0036-definition-home-library-repos-and-promote-by-pr.md`, `docs/adr/0039-provider-capability-interfaces-and-normalized-errors.md`). The **server library** is the union of the packaged/configured `definitions/` directory and every library repo's definitions; ids stay unique across all of them. **Promote** takes a workspace definition and opens one Pull Request per selected library repo, adding the definition folder for the repo's code owner to review — it never writes to a library repo directly. _Avoid_: "promote" for copying elements between definitions (that's **Copy**); treating a library repo as writable from the editor other than through a Promote PR

**Element**: The umbrella term for the four parts of a definition — Stage, Artefact, Module and Field — when a statement applies to all of them (for example "copy an element from another definition"). _Avoid_: "element" for anything that isn't one of those four, including a template, a gate, or a definition itself

**Copy (of an element)**: Pulling a Stage, Artefact, Module or Field from a **source definition** (any server-library definition, or another definition in the same workspace) into the definition being edited. A copy is independent afterwards — the source changing never changes the copy — and carries **provenance**: which definition, version and element it came from. Copying a stage or artefact also brings any modules (and, for an artefact, its template) the target doesn't already have, after confirmation. _Avoid_: "link", "reference" or "import" for this (there is no live cross-definition reference); "copy" for reusing a module *within* one definition (that's a shared module, listed by several stages)

**Field visibility per artefact**: Which of a module's fields an artefact shows and requires is set by that artefact's `requires` list, at field grain (`module.field`, or `module.field?` for optional-in-scope), and the module editor's Artefact filter honours it. A stage lists whole modules only; "shown in SOAP but not in HLD" is an artefact-requires fact, not a stage fact. _Avoid_: stage-scoped field lists (there are none); duplicating a field so a second stage can show it (see **Module completeness by gate, not by authorship**)

**Read-only Module** / **home Stage** (`docs/adr/0050-read-only-carried-forward-modules-are-an-explicit-stage-subset.md`): A Module a Stage lists under `read-only-modules:` — a subset of its `modules` it mounts only so its documents can render and its Gate can be evaluated, carried forward from an earlier Stage that owns it. The gate check and the renderer read `modules` exactly as before; only editing changes: the instance editor shows the Module's saved content with no editors or required markers, and the server (and so the MCP server) refuses a write to it at that Stage. Its **home Stage** is the nearest earlier Stage that mounts it and doesn't list it read-only — where the editor's note, and the server's refusal, send the author. Opt-in and explicit: nothing is inferred from Stage order. _Avoid_: inferring read-only from a Module appearing at an earlier Stage (it breaks progressively filled Modules — see **Module completeness by gate, not by authorship**); "locked" or "frozen" (nothing about the content changes, only where it is edited); read-only per Field (it is per Module; use `required-at` to stop a carried Field being required later)

**Stage advancement**: How an instance moves to its next stage — always explicit, never implicit, and split purely by whether the instance is local or Workspace-backed (`docs/adr/0014-pull-request-stage-approval.md`, superseding ADR-0012's ticketing-mode mechanism). A local instance advances self-serve via "Advance to next stage"; a Workspace-backed instance advances only when its stage's Pull Request merges. In both modes the action is blocked until the current stage's gate has genuinely passed. _Avoid_: treating a passed gate as if it advances anything by itself — a gate passing merely *permits* the explicit action; also avoid per-instance opt-outs from the PR requirement (there are none)

**Stage branch**: A remote stage's own branch on its **Provider**, `gantry-workspace/<slug>/<stageId>` — created the moment a stage's first save lands, targeted by every read/write while the stage is open, and stacked on the nearest earlier stage's branch that exists while that stage's PR is still unmerged. `main` only ever reflects fully-approved, merged stages. A completed stage has no branch unless re-opened (`docs/adr/0026-reopen-signed-off-stage.md`). _Avoid_: forking each stage's branch fresh from `main`, or creating the branch only at approval time

**Re-open a signed-off stage** (WI265, `docs/adr/0026-reopen-signed-off-stage.md`): A Workspace-backed completed stage — one the instance has advanced past — can be re-opened for late edits via a **Re-open stage** button shown only when free-browsing that completed stage, gated behind the same PAT/permission check as "Request sign-off". Re-opening recreates the stage branch from current `main`, moves the instance's `stage` pointer back to that stage, and records `reopened: { <stageId>: { at, previousStage } }` on `instance.yaml` — prior `pullRequests`/`workItem` records are preserved, not deleted. The re-opened stage then completes through the existing `requestStageApproval`/`checkStageApprovalStatus` machinery; on merge the marker is cleared and the instance re-advances. Re-opening is blocked if any later stage already has a branch or the instance is more than one stage past the target. Audited via a commit on the stage branch and, when linked, a work-item state/comment push. _Avoid_: treating a completed stage's leftover branch as still needing sync (it doesn't exist unless re-opened), silently overwriting prior approval history, or auto-rebasing later in-progress stages

**Instance number** / **Stage number** / **Workspace number** (WI200, docs/adr/0024): short, scoped, sequential integer references layered on top of today's identifiers, used as the canonical URL form — not a replacement for slugs (still the directory name and registry key) or stage ids (still embedded in Stage branch names). Instance numbering restarts at 1 within each workspace; stage numbering follows each instance's own definition order; workspace numbering, having no parent, is one global sequence. A URL naming a workspace but no instance defaults to that workspace's instance 1; one naming an instance but no stage defaults to that instance's stage 1. Old slug/stage-id query params keep working as a fallback. _Avoid_: treating these as global ids (they're per-parent ordinals, "start from 1" only makes sense that way), or as a rename of slugs/stage-ids (both stay as-is; this is a layered lookup, same pattern `workspaceRegistry.js` already uses for workspace UUIDs)

**Merged, not recorded** (v0.13.0, #144; `docs/adr/0014-pull-request-stage-approval.md`, `docs/adr/0026-reopen-signed-off-stage.md`; `lib/mergedApproval.js`): A remote Instance's current stage whose approval Pull Request has been merged on the **Provider** while Gantry has not recorded the approval (nobody pressed Check status). The stage page shows a notice, read from the Pull Request's status on page load as `mergedApproval` in `GET /api/instance` (a read; **prompt only**: loading never records, per ADR-0014). Two one-click actions on `POST /api/instance/stage/record-approval`: **Record approval and move on** (what Check status does for a merged Pull Request) and **Record approval and re-open for changes** (that, then ADR-0026's re-open, so the Instance ends on the same stage with a fresh branch from `main` and the approval history kept). Re-open keeps ADR-0026's guard, checked before anything is recorded: a later stage with a branch (including one drafted ahead, ADR-0063) or the stage's own leftover branch disables it with the reason, and the final stage has nothing to re-open. The action refuses a Pull Request that is not merged. Same on Azure DevOps, GitHub and GitLab. _Avoid_: recording on page load or by polling; treating this as a second kind of approval (it is the same Check status outcome, reached by an explicit click).

**Changed since approval** / **Re-approval** (v0.13.0; `docs/adr/0069-a-later-stage-re-approves-the-earlier-stage-fields-it-changes.md`): An approved stage of a remote Instance is **changed since approval** when a later stage changes a Field one of its Artefacts prints. Gantry compares the Instance's current content (the current stage's branch, else `main`) with the content at the merge commit of the stage's recorded approval Pull Request, so an Instance approved before the rule existed is covered with nothing stored; the flag shows on the stage tab, the stage status, the sign-off line ("also re-approves SOAP: 2 Fields"), the dashboard row and MCP `check_status` (`changedSinceApproval`), and never on a local or server workspace. The later stage's approval then **re-approves** it (#275): the Pull Request lists the earlier stage's changed Fields, the person who approved the earlier stage's own Pull Request joins as an extra required reviewer (Gantry keeps one required reviewer per Instance, so the earlier reviewer is read off that earlier Pull Request), and Check status waits for both votes (`waitingForReviewers`, held at pending; a changes-requested vote also waits). After the merge the earlier stage keeps its original approval and gains a `reapprovals` entry in `instance.yaml` (which stage, which Pull Request, which Fields, which reviewers, when), its linked work item gets a comment, and its flag clears because the merge commit of the re-approving Pull Request becomes the content it is compared against. Request approval also refuses until each earlier Artefact that prints a changed Field has been re-rendered on the later stage's branch (#276; the refusal lists them and offers "Render onto this stage", MCP `rerender_earlier_artefact`): the document as it was approved moves to `out/approved/`, named with its approval date (`SOAP — approved 2026-10-12.docx`), and the new render takes the usual name, so the usual name always means the currently approved version; a Field changed after the re-render makes it stale again. **Restore approved text** (#274) is the editor's way back: on the current stage, each flagged Field shows its approved and current text side by side, and restoring writes the approved wording as an ordinary Save on the later stage's branch (so it goes through the Save check, ADR-0068); the flag clears once no flagged Field differs. _Avoid_: "invalidated" for this (that's an open Pull Request's approval going stale when a commit lands after the vote, ADR-0018); "re-open" (re-approval happens without re-opening the earlier stage); counting a change to a Field only later Artefacts print

**Request approval** / **Check status**: The Assignee-side pair gating a remote stage. Request approval opens that stage's Pull Request into `main` — the actual approval gate — once its gate has passed; Check status explicitly reads the PR's reviewer votes, distinguishing a rejection or changes-requested vote from a merely-still-pending review, and on detecting approval gantry completes (merges) the PR itself, advances the stage pointer, and pushes any linked work item's state. The Owner approves directly on the **Provider**. On GitHub, `APPROVED` and `CHANGES_REQUESTED` map to their gantry equivalents while `COMMENTED` and `DISMISSED` read as still-pending, gantry merges with a merge commit, and a branch-protection refusal surfaces verbatim as a blocked sign-off (`docs/adr/0040-github-work-item-and-review-model.md`). GitLab has no formal "request changes" review verb on Free/CE (only an Approve/unapprove toggle, structurally separate from discussion threads) — gantry reads *not-approved-with-an-unresolved-discussion-thread* as the CHANGES_REQUESTED-equivalent, *not-approved-with-no-unresolved-thread* as still-pending (COMMENTED-equivalent), and on GitLab Premium/Ultimate instances additionally honours enforced Approval Rules where present, falling back to the toggle-plus-threads reading where they're not (`docs/adr/0041-gitlab-as-third-provider.md`). Bitbucket Cloud's pull request needs no such workaround — each reviewer carries a genuine tri-state (`approved` / `changes_requested` / no action yet) that maps directly onto gantry's approved / CHANGES_REQUESTED / still-pending the same way GitHub's does (`docs/adr/0042-atlassian-as-fourth-provider.md`). Approvals go in stage order (`docs/adr/0063-drafting-ahead-approvals-in-stage-order-shared-modules-wait.md`): both actions only act on the instance's current stage on `main`. Request approval for any other stage is refused, naming the current stage, and Check status on an approved Pull Request for a stage that is not current merges and advances nothing and reports that the stage waits for the earlier one. Surfaced in the UI as "Request Sign-off" / "Review / Sign-off" (WI197, docs/adr/0023) — see **Request Review** below for the differently-named, differently-behaved concept those labels sit next to. _Avoid_: polling or webhook-based approval detection (explicitly rejected — detection stays manual), adding an approve button inside gantry, or reading the linked work item as gating advancement (it is a tracking surface only; the PR gates)

**Check gate & sync work item**: A second, independent linked-work-item push — distinct from Check status's own automatic push above. Triggered by the *current stage's content gate* passing (module completeness, independent of any Pull Request), it checks the gate and, only on an explicit confirm click, pushes the gate-passed state to the linked work item. Available for any instance with a linked work item, local or Workspace-backed alike (a local instance has only this action; a Workspace-backed instance has both this and Check status, side by side). WI217 folds this in as a second step of the one Check status click for a Workspace-backed instance — first the Check status refresh/approval-detection sequence runs, then (only if that didn't just advance the stage) the gate-check-and-confirm-sync step — while a local instance keeps this as its own, sole, unchanged button. _Avoid_: conflating this confirm-gated, content-gate-driven push with Check status's own unconfirmed, PR-merge-driven push above — they fire on different triggers and keep their separate confirmation postures even once combined into one entry point

**Request Review**: A remote stage's informal, non-gating request for feedback (WI197, docs/adr/0023) — distinct from Sign-off (**Request approval** / **Check status** above), which gates stage advancement. Sending a request creates one work item per reviewer (never a shared item), related-linked to the stage's own linked work item, on every **Provider** — on Azure DevOps because `AssignedTo` holds one person, and on GitHub, GitLab and Jira (Atlassian's own work-items half) deliberately in the same shape even though GitHub/GitLab issues take several assignees, so per-reviewer status stays expressible and the concept stays single-meaning (`docs/adr/0040-github-work-item-and-review-model.md`, applied to GitLab's own Issues by `docs/adr/0041-gitlab-as-third-provider.md` and to Jira's own Issues by `docs/adr/0042-atlassian-as-fourth-provider.md`). Status rides reserved `gantry:review/<status>` labels on GitHub, GitLab and Jira alike, identical vocabulary and slugs on all three, since it's one gantry-owned convention layered onto three issue trackers, not a per-provider naming choice — created on demand for GitHub/GitLab (a repo/project-level label registry both require before use), while Jira's own `labels` field is freeform and needs no such registry step first. Assignment on GitLab is by numeric user id (`assignee_ids`, GitLab's Issues API having no assign-by-username field the way GitHub's does); assignment on Jira is by its own opaque `accountId` (per ADR-0042/#45), resolved against **Jira's** own user directory, never Bitbucket's — reviewer identity for this action always comes from whichever product's work items the request creates, not the pull-request-reviewer half of a split-suite **Provider**. A review's status is read via an explicit "Check status" action, never polling. Available at any time during the stage — not gated behind the gate passing, unlike Sign-off. Review and sign-off statuses both surface on the Work item details card, scoped to the currently-viewed stage only. _Avoid_: confusing this reviewer (an informal feedback request, no bearing on advancement) with Sign-off's own required reviewer (the Pull Request's gating vote, #145/ADR-0014) — different people, different mechanisms, different work items; also avoid reading "sign-off" here as the unrelated module-frontmatter `status`/`owner` convention (**Document history and sign-off** below) — that's document-authoring metadata, this is a stage-level action

**"+ New Workspace" wizard**: The landing page's sole creation entry point (`/new-workspace`, `docs/adr/0013-unified-workspace-creation-wizard.md`): pick an existing workspace or register a new one (setting its Owner then, too), then instance Name + Directory (defaulting to the slugified Name) + initial Assignee, then — only for a workspace whose **Provider** tracks work items — the parent-work-item link, with the workspace's own location pinned read-only and the remaining fields as PAT-backed lookups. Registering a new workspace picks its **Provider** first, since that decides the location fields collected (Organization/Project/Repository for Azure DevOps, Owner/Repository for GitHub, Namespace/Project for GitLab — GitLab's "Namespace" is the full group/subgroup path, however many segments deep, treated as one opaque string rather than split per level; "Project" is shown with GitLab's own label but stored as `location.repository`, the same key GitHub's location uses, since a GitLab Project is structurally what GitHub calls a repository; Bitbucket Account/Repository plus Jira Site/Project for Atlassian — the wizard collects both halves of the split suite at once, "Bitbucket Account" stored as `location.owner` the same key GitHub's location uses since Bitbucket Cloud addresses a repo identically, "Jira Site" and "Jira Project" stored as `location.jiraSite`/`location.jiraProjectKey`) and the work-item fields offered (neither GitHub nor GitLab has a work-item *type*, so that field is omitted rather than emulated — `docs/adr/0040-github-work-item-and-review-model.md`, `docs/adr/0041-gitlab-as-third-provider.md` — while Jira, like Azure DevOps, requires one, so the wizard fetches that Jira project's own configured issue types live and offers the same kind of picker Azure DevOps already has, rather than a hardcoded value — `docs/adr/0042-atlassian-as-fourth-provider.md`). The PAT entered to validate the repo becomes that workspace's **Workspace PAT** on successful creation — for Atlassian this step collects both the Bitbucket and the Jira token before the workspace validates, since the suite is split. _Avoid_: calling it the "setup wizard" or "+ New instance" (both removed), or pasting a raw repo URL as the starting point

**User Guide** (WI183, pending): The app's own in-product help page — end-user-facing (creating workspaces, advancing stages, requesting approval), distinct from `README.md`, which stays contributor/dev-facing (repo setup, architecture, the engine's own vocabulary for people extending gantry). Teaches the engine's generic concepts (Definition, Stage, Gate, Module, Instance, Artefact) using the `design` definition as its worked example throughout, not a manual specific to `design` — written so it doesn't need a rewrite the day a second definition is added. Its stage/gate and artefact reference sections read from each stage/artefact's own `purpose` field (docs/adr/0022) rather than duplicating explanatory prose disconnected from the definition; its module/field content stays conceptual with 1-2 worked examples, not an exhaustive per-module catalog. Content lives as markdown files under `docs/user-guide/`, rendered through the app's existing markdown pipeline. Linked from the header on both the landing page and instance pages, to the left of Settings. _Avoid_: duplicating README's contributor-facing text wholesale — the User Guide covers overlapping concepts in end-user language, from scratch, not by copying README's prose; treating it as `design`-specific documentation; an exhaustive module-by-module catalog

**Archive / restore** (WI223): A reversible "set aside" for a Workspace or an Instance, driven from its Settings screen. Archiving sets `archived: true` on the registry entry (`lib/workspaceRegistry.js` / `lib/instanceRegistry.js`) — nothing on disk or on the **Provider** is deleted — and the item drops out of the default dashboard and API listings; `?archived=1` / `includeArchived` is the explicit opt-in that shows archived items again, each for a per-row Restore that returns it to exactly its prior state. Archiving a workspace does not cascade to its instances and is blocked (409) while it still has any active instance. An archived instance still resolves read-only at its direct URL (the module editor shows it, `GET /api/instance` carries `archived: true`). _Avoid_: treating archive as a soft-delete (there is no delete; restore is always possible and lossless), or expecting a workspace archive to sweep its instances with it (each item is archived on its own)

### The MCP server

**Gantry MCP server** (`docs/adr/0043-mcp-server-is-a-separate-render-hosted-http-client.md`): A separate package, deployed as its own Render service, that lets an AI agent do everything the web UI can do via the Model Context Protocol — a thin HTTP client of a running `gantry serve`, using the same `/api/*` surface and the same per-request **Workspace PAT** auth as the browser (`docs/adr/0038`). Never imports gantry internals and holds no state of its own beyond its two credential env vars (the **MCP access token** and the **MCP workspace-PAT map**). _Avoid_: treating it as a mode of `gantry serve` or a CLI subcommand (it is neither); assuming it can reach a Local workspace (it structurally cannot — see **Workspace location**)

**MCP access token**: The single shared static bearer token gating who may call the **Gantry MCP server** at all — one env var, one tenant (today, just the person running it), entered into the AI client's own MCP connection config. Distinct from a **Workspace PAT**, which authenticates a specific workspace to its Provider rather than a caller to the MCP server itself. _Avoid_: calling this a PAT (it authenticates to gantry's own MCP layer, never to a Provider); assuming it scales to multiple people without revisiting the model (`docs/adr/0043`)

**MCP workspace-PAT map**: The env var (a JSON object, workspace → PAT) the **Gantry MCP server** reads once at startup to get each Provider-backed workspace's **Workspace PAT** — the MCP-side counterpart to the browser's per-workspace credential store, held server-side and never passed through the calling agent. A Server-hosted (non-Provider) workspace needs no entry. _Avoid_: treating this as a global/default credential (`docs/adr/0038` forbids that concept regardless of holder) — each entry is still scoped to exactly one workspace, just supplied at process start instead of per-browser-session

### The `design` definition

**Business Case Approved**: The gate closing the `shape` stage, whose display title is **SOAP**. Approves the SOAP (Solution on a Page). _Avoid_: "business case gate" (use the full canonical name in artefacts and docs)

**HLD approved by the Architecture Review Board (ARB)**: The gate closing the `hld-define` stage, whose display title is **High-level Design**. Approves the HLD (High Level Design) paper submitted to the ARB. Gate id `hld-arb-approved` (renamed 2026-09-19 from `hld-tac-approved` — see **ARB** below). _Avoid_: "design authority gate" — Design Authority is a different, later committee (see below); this gate belongs to the ARB.

**Build Readiness Confirmed**: The gate closing the Detailed Design stage. A single shared gate for both the SAD and SSAD artefacts — they are two renderings of one module set, not two independently-gated documents. _Avoid_: "Design authority" as a name for this gate — that phrase was an unresolved placeholder in the source coverage-assessment spreadsheet and has since been superseded by this canonical name.

**Operational Handover completed and submitted to the ARB for noting**: The gate closing the Handover stage. Confirms the as-built/Detailed Design documentation has been produced and handed to the ARB for noting (not approval).

**ARB (Architecture Review Board)**: The canonical name for this definition's HLD-approving governance body (renamed 2026-09-19 — "TAC" / "Technical Architecture Committee" was the prior canonical term, from the source HLD reference template's own vocabulary; the SAD template's own source material already called it "ARB approval", which is what prompted the switch to the more generic, less single-organization-specific name). Still one body, not two — a document written before this rename that says "TAC" means the same governance body as "ARB" written after it. _Avoid_: treating ARB and TAC as two distinct bodies; using "TAC" in any new text — the gate id, glossary, module guidance and example instance content were all updated together, so nothing current should still read "TAC"

**Design Authority**: A governance committee distinct from the ARB. Reviews the `sad`/`ssad` artefacts (via the architecture-related modules) before the Build Readiness Confirmed gate is reached. Not itself a gate — tracked via module frontmatter `status`/`owner`, not a stage exit point. _Avoid_: using "Design Authority" as a gate name — it is a review step, not a gate. This role is a stated intent (Chris Barlow, 2026-08-17), not yet corroborated by a charter or terms of reference.

**Architecture Decision (AD)** (design v3, #200, #308): One design decision in a design instance, recorded as a **Key decision** in the Key decisions standard module (`key-decisions.decisions`, carried from the SAD into the As-built as one list) with the prefix `AD` and the WH(Y) style, numbered AD01, AD02, … and keeping its number when decisions are reordered or removed. (design v1 and v2 recorded them in an `| AD | Decision | ADR |` table, `architecture.design-decisions`, carried into `as-built-notes.architecture-decisions`.) Every decision is an AD. Only an AD that needs governance endorsement — enterprise reuse, a new platform or product, a new architecture precedent, or endorsement explicitly required — also names an **ADR** (Architecture Decision Record), written at the end of its title as the placeholder `ADRYYY` until the ADR is registered, and then its number. That rule is design's own, in its Key decisions guidance and Interview instructions; Gantry's Key decisions module does not know it. An ADR does not by itself go to the **ARB** either. _Avoid_: treating every design decision as an ADR, or every ADR as an ARB agenda item; confusing a design instance's ADRs, which belong to the organisation using Gantry, with this repo's own `docs/adr` records about Gantry itself

**SOAP (Solution on a Page)**: In this definition, specifically the artefact for the `shape` stage (whose display title is **SOAP**), rendered from `context`, `solution-definition` and `team-and-estimates` — modelled on the real Confluence Epic SOAP structure. A *different* document, the ARB's own "High Level Solution Design" template, is modelled separately as the `hld` artefact — the two are not the same thing despite both sometimes being called "SOAP" informally. The template's own real title still names its source committee historically (see docs/adr/0032 — that citation is unchanged by the ARB rename, since it names an actual external document, not gantry's own vocabulary). _Avoid_: using "SOAP" to mean the HLD paper

**Full SOAP**: A second, heavier `shape`-stage artefact (`soap-full`) alongside `soap` — a fuller variant of the *same* Confluence Epic SOAP family (`reference/current_design_artefacts/JEDI-Full SOAP Template-240826-023808.pdf`), not the HLD paper. Reuses `soap`'s own modules (`context`, `solution-definition`, `team-and-estimates`) plus the existing `dependencies` module, extended with fields `soap` doesn't require — see docs/adr/0020. Either `soap` or `soap-full` being complete closes Business Case Approved (docs/adr/0019); authoring both is never required. _Avoid_: treating Full SOAP as a replacement for SOAP, or as the same document as HLD

**SAD (Solution Architecture Document) / SSAD (Solution Support Architecture Document)**: Two artefacts at the Build Readiness Confirmed gate, rendered from the *same* shared module data (`architecture`, `integration`, `data`, `nfrs`, `security`, `risks`, `dependencies`, `support-and-operations`) but with distinct, field-accurate `requires` lists in `definitions/design/definition.yaml`. **Corrected 2026-08-27** (docs/adr/0021, implemented WI181): the two artefacts' `requires` were previously byte-identical, which didn't match the real source documents. `SAD Template.docx` (`reference/current_design_artefacts/`) is an extensive, infrastructure/architecture-heavy blank template — Business Architecture View, Technology Architecture View, Deployment View, Data View, Security View, Operating Considerations — running to ~20 major sections. `FV Help Tool SSAD.docx` (one real filled example, not a template — no blank SSAD template exists) has a genuinely different section list (Solution Products, Architectural Risks, Solution Overview: Stakeholders/Domains/URLs/Environments/Security/Release Procedures). SAD and SSAD are still two renderings of one underlying design (SSAD is support-facing framing of the same solution, not a structurally independent document, per docs/adr/0001) — SAD now requires the complete architecture/requirements/security/dependency views plus only a support-handover summary, while SSAD requires full operational readiness plus only the design fields its support-oriented template actually presents. _Avoid_: treating SAD and SSAD as needing entirely independent module sets (they still share underlying design content, per docs/adr/0001) — the fix is per-artefact field-level `requires` filtering, not a structural split

**Gate-passing is per-artefact, not per-stage-module-list**: A gate passes when *at least one* of its gate-matching artefacts that **satisfies the gate** has its own `requires` fields complete — not when a stage's full `modules` list is complete (docs/adr/0019, amended by docs/adr/0051). `stage.modules` still drives the union of modules available for authoring, while each artefact's field-level requirements drive its own completeness and the editor's optional artefact filter. _Avoid_: assuming a stage's gate needs every one of its artefacts fully authored — only one needs to be

**Satisfies the gate** (`satisfies-gate`; #151, `docs/adr/0051-an-artefact-can-be-excluded-from-satisfying-its-gate.md`): Whether completing an Artefact passes its Gate. Every Artefact does by default. One that sets `satisfies-gate: false`, shown as the unticked **Completing this artefact passes its gate** checkbox on the Definitions page, is still evaluated, reported, rendered and linked in the approval request when complete, but never passes the Gate on its own. It is meant for an audience document, such as a candidate's Appointment Confirmation, that carries only what its reader needs and so must not be the easy way through the Gate. The gate check reports it as `satisfiesGate: false`, the instance editor hints "doesn't count toward the gate", and a failed Gate names the closest incomplete Artefact that *does* satisfy it. A Stage whose Artefacts all opt out is an `unsatisfiable-gate` problem; a Stage with no Artefacts is not. _Avoid_: reading "an Artefact at this Gate is complete" as "the Gate passed"; opting out an Artefact whose Fields no satisfying Artefact at the same Gate also requires (the Gate would then pass without them)

**Module completeness by gate, not by authorship**: `nfrs`, `risks`, `security` and `dependencies` are each a single module required at two gates (`hld-arb-approved` and `build-ready-checklist`), filled in progressively — not duplicated as separate lightweight/full versions. Where a field's requiredness genuinely differs between the two gates, that's expressed with the module-spec schema's `required-at` key (see README.md "Field requiredness across shared gates"), not by splitting the field or the module. Most `nfrs` and all `security` fields use `required-at: [build-ready-checklist]`; `risks.risk-register` is required at both gates as-is, since only its expected depth — not its requiredness — changes; `dependencies` uses two distinct fields (`dependencies-overview` required-at `hld-arb-approved`, `dependency-list` required-at `build-ready-checklist`) since the overview genuinely isn't the same shape of content as the full list, not two depths of one field. _Avoid_: creating a second module (e.g. `nfrs-detailed`) for the later gate, or treating `required-at` as a place to encode content depth rather than requiredness. A 2026-08-18 audit found `dependencies` had been built as two separate single-gate fields (`proposed-solution.dependencies` and `integration.dependencies`) instead of this pattern — see docs/adr/0003 — watch for other information categories built the same way before assuming a new module/field pair is genuinely distinct content.

**Cost-benefit vs. NFR**: Cost-benefit analysis lives in `proposed-solution` (the `hld-define` stage, whose display title is **High-level Design**), not in `nfrs`. It's a one-off business justification for the HLD decision, not a quality attribute the built solution must keep meeting. _Avoid_: adding cost-benefit content to `nfrs` — that module is for performance/availability/scalability-type requirements only

**Disaster recovery and backup vs. support-and-operations**: RTO/RPO, backup schedule and retention live in the shared `nfrs` module (`disaster-recovery-and-backup`), not in `support-and-operations` — it's a quality attribute of the built solution, not a support-team-specific concern, even though a 2026-08-18 gap review found it via a real SSAD example. _Avoid_: duplicating backup/retention content in `support-and-operations`

**Document history and sign-off**: Revision history and formal sign-off for a module are tracked via the instance module file's frontmatter `status`/`owner` convention and this repo's git history — not a module field. _Avoid_: adding a `sign-off` or `revision-history` field to any module

**Field ("Section" in the UI)**: A labelled markdown block inside a module (e.g. `problem-statement`'s "Current state"), edited directly in the module editor. Users add new ones via Insert → Section — these custom fields are ordinary fields with an optional title. _Avoid_: "Section" in code identifiers, storage, or API names — Section is UI copy only, never a distinct concept from Field

**Field type (`markdown` / `list` / `select` / `text` / `date`)** (`docs/adr/0044-typed-module-fields-select-text-date.md`): The closed vocabulary a Field's `type:` is drawn from — validated identically by the server-side Definition loader and its Local-Workspace twin, with an unrecognised value a hard error rather than a silent free-text fallback (a deliberate choice: an older Gantry refuses a Definition using a type it doesn't know, rather than quietly losing the constraint). `markdown` (prose) and `list` (a bullet list) are the original two; `select`, `text` and `date` (#90, epic #77) are three more, added because a fixed enumeration stated only in guidance prose is advisory, not enforced, and because naming a rendered document (see **Filename pattern** below) needs a short single-line value no earlier type produced. A `select` carries an **Option** list (below); `select` with `multiple: true` is a variation within the type, not a second type name, storing several chosen values as bullets exactly as `list` already does. `text` is one line; `date` is a calendar date authored through a date picker and stored as ISO 8601 (`YYYY-MM-DD`) — canonical because it sorts correctly in a folder listing and diffs cleanly; templates get a `formatDate()` helper so a rendered document can read naturally ("3 November 2026") without a second stored value ever existing to disagree with the stored one. _Avoid_: inventing a field-shape check elsewhere in the codebase instead of going through `lib/fieldShape.js` / `web/lib/fieldShape.js`'s `isMultiValuedField`/`emptyFieldValue`/`parseFieldBody`/`serialiseFieldBody` (the one place that knows which types are multi-valued); assuming `select`'s stored value is anything but the option string verbatim (see **Option** below)

**Option**: A `select` Field's permitted answer, declared under `options:` as a plain string — no key/label indirection, since the chosen string is exactly what the Module file stores and what a rendered document interpolates (`docs/adr/0044`). An optional `default:` names one option to pre-select in the Stage editor; it takes effect by being written to the Module file on that module's *first save*, never at Instance creation, so an Instance nobody has opened still can't satisfy a required Field on a choice nobody made. A value already on disk that isn't in the current option list — hand-edited, or left behind by a Definition's options changing — is preserved and shown as a marked extra entry rather than dropped, and is reported as a warning by `check` without blocking the Gate, the same rule the Module parser already applies to an unrecognised heading. There is no "Other" escape hatch: where a Field's guidance names a classification *and* asks for a qualifying sentence, the Definition splits it into a `select` plus a separate prose Field beside it (`recruitment-onboarding/2`'s `selection.candidate-name` + `selection.rationale` is a worked example) rather than adding an open-ended option that would let the enumeration rot back into free text. _Avoid_: renaming an option in a published Definition version (versions are immutable; renaming an option is a new version by construction); designing a Field around "mostly closed, with an escape hatch" — that's the case ADR-0044 rules out

**Instance settings** (#219, spec #223, `docs/adr/0058-instance-settings-are-declared-by-the-definition.md`): The group of per-Instance choices a **Definition declares**, each with an id, its **choices** and an optional **default**. Each applies to the whole Instance, not to one Stage's content. Two members: **Target size**, and **Classification** (#220), the marking every document of the Instance carries, whose choices are the Definition's own markings, stored verbatim (the **Option** rule). A Definition declares the settings it offers under `instance-settings:` in `definition.yaml` (`classification: { choices: [...], default: ... }`, and `size: { default: ... }` for Size, whose choices are Gantry's, #221); Size is offered only because some Field declares word targets. A malformed declaration (no choices, a blank or duplicated marking, a default that isn't a choice, Size choices of its own, a setting a Definition can't declare) is an `invalid-instance-settings` problem that `gantry validate`, a Local Workspace and the Definitions page report and Save and Publish refuse; it doesn't stop the Definition loading, and every reader ignores the malformed setting. One shared module (`web/lib/instanceSettings.js`) says, for a Definition, which settings it offers, their choices and defaults, and an Instance's effective value of each. Every surface reads that one description: the "+ New Workspace" wizard and Instance Settings show the offered settings under one "Instance settings" heading, the Definitions page has an "Instance settings" section saying why each is offered, its choices and its default, which on a draft edits each one's choices and default (#221: Classification's markings added, renamed, reordered and removed, Size's default picked, its choices shown but fixed) in the server's Definitions page and a Local Workspace's Definition editor alike, read-only once published, and Instance creation, the Instance Settings write (`PUT /api/instance/settings`, on the stage branch for every Provider and directly in a Local Workspace) and MCP refuse a setting the Definition doesn't offer or a value outside its choices. Each is stored under its own key in `instance.yaml` (`size:`, `classification:`), written only when a value is chosen; the effective value is the stored one, else the Definition's default, else the setting's own fallback (Medium; no marking). Classification is optional: with no default the wizard and Instance Settings offer None, and blank prints no marking. A Definition that offers none (design v1/v2, recruitment-onboarding) shows no Instance settings anywhere. The Instance's own **Logo** (#224) sits in the group too, under the same heading, but is file-shaped rather than choices plus a default: its default is the Definition's **Logo** and its choice an optional PNG or JPEG upload, offered only when the Definition's **Reference documents** carry a header logo. It is stored with the Instance in its `assets/` folder (`assets/instance-logo.png` or `.jpeg`) and named by `logo:` in `instance.yaml`, written only when one is uploaded; Instance Settings shows it with Replace, Download and Remove, saved on the stage branch for every Provider and directly in a Local Workspace (`PUT`/`DELETE /api/instance/logo`), and MCP `get_instance` reports `instanceLogo: { own, source }`. _Avoid_: calling Assignee or Required reviewer Instance settings (they are about people, the Definition doesn't declare them, and they keep their own routes and rules); "instance options" or "instance properties"; wiring a new per-Instance choice into each surface by hand instead of declaring it

**Target size** (#202, `docs/adr/0054-target-size-is-an-authoring-target-not-render-time-condensing.md`): An **Instance setting** (ADR-0058): how much an Instance's authors write in each Field — **Small**, **Medium** or **Large**, stored as `size:` in `instance.yaml`. Its default is the Definition's (`instance-settings: { size: { default: ... } }`, set on a draft's Definitions page, #221), else Medium: an Instance with none stored works to it, in the editor's targets, `get_instance` and the over-budget notes, and the wizard pre-selects it. A Field states its **word budget** per size with `target-words: { small, medium, large }` (positive whole numbers; markdown and list Fields only); the size picks which one applies. It is chosen in the "+ New Workspace" wizard and changed in Instance Settings, both under the "Instance settings" heading, and set by MCP `create_instance`; the Definitions page shows it as offered "because N Fields declare word targets". It appears only when the Instance's Definition declares at least one budget — a Definition with none (design v1/v2, recruitment-onboarding) shows no size anywhere. Design v3 budgets every free-text Field that renders into an Artefact (#203): Large is its example's length before condensing, Medium about half and Small about a fifth, and the bundled examples are written to Medium. The editor shows `Target ~N words (Medium)` and a live word count under each budgeted Field, amber when over; MCP `get_instance` returns each Field's target and `update_instance_modules` returns a non-blocking note per over-budget Field. Words are counted as a reader reads them: fenced code (a Mermaid diagram's source), images and Markdown punctuation don't count. It is an **authoring target, not a render-time transformation**: it never blocks a Save, a Gate or a render, and Templates, sections, Fields and rendered output are the same at every size. _Avoid_: "length", "detail level" or "verbosity" for this setting; "limit" or "maximum" for a budget (it is a target, and over-budget content is kept and rendered); condensing content at render time, or calling a model to shorten it (rejected in the ADR: an AI dependency, `IN-CONFIDENCE` content sent to a provider, and a document no longer reproducible from its commit); a size control on the Render dialog

**Filename pattern** (`docs/adr/0045-rendered-artefacts-name-themselves-from-instance-content.md`): An optional `filename:` string on an Artefact, containing `{module.field}` tokens resolved against an Instance's own content at render time, replacing the default `<Instance name> - <Artefact title>` scheme for that Artefact alone. A token may reference `{today}` (the date of *this* render, not a frozen first-render date), `{instance.name}`, `{instance.slug}`, or a single-valued **select**, `text` or `date` Field (never `markdown`, `list`, or a `multiple: true` select, which store more than the one string a filename position can hold) — and every Field a pattern references must already be in that Artefact's own `requires` list, both checked at Definition-publish time so a bad token is an authoring error caught on the branch, never a render-time surprise with someone waiting on a document. A token whose Field is still blank simply drops out of the resolved name, tidied of its surrounding separators — rendering a draft mid-stage, before every Field is filled, is not blocked by this. The resolved name is sanitised the same way every rendered filename already is (path-hostile characters replaced, whitespace collapsed, length-capped) and stays human-readable — never slugified — since the whole point is a document that identifies itself to someone who has never heard of Gantry. All of this lives in exactly one place, `renderedArtefactBasename`, for the local path and every Provider push alike. _Avoid_: a pattern referencing a Field outside the Artefact's own `requires` (rejected at publish, not truncated at render); expecting `{today}` to freeze at an Artefact's first render (it doesn't — see the ADR §3); confusing this with the **render manifest** below, which is what keeps a *changing* resolved name from leaving stale files behind

**Document Control (block)** (WI233; `docs/adr/0049-an-artefact-can-leave-out-document-control.md`): The two tables the render pipeline puts straight under a rendered document's title. **Document Control** lists version, date, the commit the render was pushed as and gate status. **Review & sign-off** has one row per review and sign-off, or a single `Pending` row. They are supplied by Gantry, not authored as Fields, and appear on every document by default. There are two ways to leave them out. A Definition can clear the block for all its Artefacts with an empty `templates/_documentControl.md.tmpl`. One Artefact can set `document-control: false`, shown as the **Document Control** checkbox on the Definitions page. Either way the H1 stays. The per-Artefact switch is meant for documents that leave the organisation, such as a candidate's Offer Pack. The key takes only `true` or `false`; any other value is an `invalid-document-control` problem. _Avoid_: calling this block "sign-off" in the sense of **Request approval** (the table reports that sign-off; it isn't the mechanism); switching it off for a document the organisation keeps for itself (the commit reference is what ties the document to its audit trail); authoring version, date or approver sections as Fields to stand in for it

**Cover page** (`cover-page`; #194, `docs/adr/0052-an-artefact-can-open-with-a-cover-page-and-a-table-of-contents.md`): An optional first page the render pipeline puts on a document, switched on per Artefact with `cover-page: true`, shown as the **Cover page** checkbox on the Definitions page. It shows a classification, the instance's display name as the title, the Artefact's title as the document type, the version and status the **Document Control (block)** prints, the instance's Assignee as author and the Artefact's `cover-purpose`, then a page break; Document Control follows it. The classification is the Instance's **Classification** **Instance setting** when the Definition declares classification markings (#220, ADR-0058), and is left out when it is blank. Only for a Definition that declares no markings does it come from the Field the Artefact names with `cover-classification: <module>.<field>`, which must be a single-valued `select` or `text` Field in that Artefact's own `requires`, and is left out when the key or the value is absent: a fallback for Definitions written before Instance settings, which the Definitions page no longer offers. design v3 prints that cover line invisibly and shows the classification only in its page header, which reads the line with a `STYLEREF` field (#207, #209). The **cover purpose** (`cover-purpose`; #205) is a statement for the reader of what the document is ("This document describes …"), set per Artefact beside the checkbox; without one the cover has no purpose line. Supplied by Gantry, never authored as Fields, and off by default. The switch takes only `true` or `false` (`invalid-cover-page`); a bad pointer is `invalid-cover-classification`; a blank or non-string cover purpose is `invalid-cover-purpose`. _Avoid_: a Module or Field to hold the classification (it is an Instance setting); printing the Artefact's `purpose` on the cover (it is an instruction to the author, for the **User Guide** and the Definitions page, and the cover never falls back to it); putting diagrams or section content on it (it reads only the instance record, the Artefact spec and the Document Control values); authoring title, version or author Fields to stand in for it; expecting a template's own `#` title line to move onto the cover (it stays where the template put it, after the front matter)

**Reference document** (`templates/reference.docx`, `templates/reference-<artefact>.docx`; #197, `docs/adr/0056-word-formatting-lives-in-the-reference-document-and-unnumbered-headings-switch-numbering-off.md`): The Word document a Definition ships for each Artefact, whose styles a render pours the compiled text into. It decides every part of a rendered document's look: fonts, colours, heading numbering, keep-with-next, the `Table` style every table uses, and the headers and footers. An Artefact uses `reference-<artefact>.docx` when it exists and `reference.docx` otherwise, on every render path. It is replaced per Artefact under **Reference docx** on a draft's Definitions page, which is how an organisation applies its **house style**. Its page-header picture is the Definition's **Logo**, which the Definitions page's **Logo** control replaces in every reference document at once. An Instance with a **Logo** of its own (#224) renders from a copy of the reference document with that logo in the header, made at render time on every render path; the Definition's files are never changed and the output is never post-processed. A heading the reference document would number is left unnumbered with Pandoc's `{.unnumbered}` class, in a Definition's Document Control partial or in any Artefact that turns on a cover page, table of contents or diagram captions. _Avoid_: formatting a rendered document by hand (the next render loses it); post-processing the `.docx` (every rule is a style); "template" for this file (a template is the `.md.tmpl` that lays out the content)

**Logo** (#222, `docs/adr/0059-a-definitions-logo-lives-in-its-reference-documents.md`): The picture in the page header of a Definition's **Reference documents**: one per Definition, so one per organisation, since each keeps its own copy. Design v3's is the Contoso logo. The **Logo** control on the Definitions page shows it with Download, and on a draft offers Replace: a PNG or JPEG uploaded there is written into every reference document of that version at once, the shared one and each Artefact's, keeping its proportions inside the space the old picture took up, with "Organisation logo" as its alt text. Every picture in a header is the logo, whatever it is called; a reference document with none is left as it is, and the control says so. It is applied when uploaded, never at render time, so a reference document uploaded later under **Reference docx** keeps its own. A Local Workspace's Definition editor has the same control. An Instance can override it with a logo of its own (#224, an **Instance setting**): its documents show the Instance's logo, else the Definition's, else whatever the reference document ships with (Contoso for design v3). _Avoid_: a deployment-wide logo (rejected in the ADR); expecting the Definition's logo in an Instance that has uploaded its own; replacing the logo in each reference document by hand

**Table of contents** (`table-of-contents`; #194, `docs/adr/0052-an-artefact-can-open-with-a-cover-page-and-a-table-of-contents.md`): An optional "Table of Contents" heading and Word TOC field (heading levels 1–3) the render pipeline puts on a document, switched on per Artefact with `table-of-contents: true`, shown as the **Table of contents** checkbox on the Definitions page. It goes after the **Document Control (block)** and before the first section, then a page break. With `document-control: false` it takes Document Control's place: straight after the **Cover page**, or first under the title when there is none. The render fills the field in (#206): one entry per heading at levels 1–3, in order, in the `TOC 1`–`TOC 3` styles, each linked to its heading's bookmark and numbered as the **Reference document** numbers its headings, so it reads in any viewer. It has no page numbers; Word adds them when it rebuilds the field on opening the document (the field stays marked dirty). With no heading to list it holds a one-line placeholder. It is a Word field inserted in the shared compile step, not Pandoc's `--toc`. The key takes only `true` or `false` (`invalid-table-of-contents`). _Avoid_: expecting the `.md` render to show a list of sections (it carries the field for Word, not the contents); adding Pandoc's `--toc` to a render path (it would put the contents before Document Control); expecting page numbers before Word updates the field (they need a page layout); post-processing the `.docx` to fill it in (the compile step does)

**Render manifest** (`docs/adr/0045` §7; tracked as issue #88, not yet built): The planned small bookkeeping file under an Instance's `out/` directory recording which file is each Artefact's *current* rendered document. **Filename pattern** (above) means a document's resolved name can now change between renders — a corrected candidate name, a moved start date — and, separately, renaming an Instance has always changed the default `<Instance name> - <Artefact title>` name with nothing anywhere cleaning up the file left behind under the old one. The manifest is the mechanism meant to fix both: a render whose resolved name differs from the previous one is to write the new file and delete the superseded one in the same commit, so `out/` keeps holding exactly one current document per Artefact and the repository's own history stays the audit trail for what changed. _Avoid_: assuming this already runs — until issue #88 lands, a name-affecting re-render leaves the previous file in place, and `recruitment-onboarding/2`'s own user guide coverage says so plainly rather than describing the intended behaviour as current

**Environment (UAT, Production, …)**: Content, not a data-model dimension. An instance has no environment axis — one instance describes one initiative, and the environments that initiative will run in are described *inside* its fields (in v2 canonically `support-and-operations.environments-and-domains`, and at SOAP level in the solution overview and diagrams). The bundled `gantry` instance (`workspaces/examples/gantry`, WI #354) is the worked example: one instance, with UAT and Production (Azure Container Apps) as prose and Mermaid diagrams in `solution-definition`. _Avoid_: adding a per-instance environment field, branch or registry key; creating one instance per environment for a single initiative; confusing "environment" with **Stage** (the process axis Gantry does model) or with **Workspace location**

**Source document** (v0.13.0, being planned): A file the architect uploads to an Instance, or that the Gantry server fetched from a web address the architect (or an outside agent) gave, as a snapshot (#318, v0.14.0; `docs/adr/0071`; **Add from address**: its **origin** is recorded with it; it is otherwise the same thing, stored, listed, cited, renamed, removed, replaced and flagged Out of date the same way, and an HTML page is a kind only an address brings in), or a **pointer to a code repository** (#319, planned: a Provider repository and branch, read live and never copied into the Instance; each read records the commit it saw, which is what a citation names), as input to its design — a brief, requirements, meeting notes, an existing architecture, a spreadsheet, a screenshot — kept with the Instance as the evidence its content is drawn from, and cited by name wherever a figure or decision came from it. Kept in the Instance's flat `sources/` folder with a `sources/manifest.yaml` (fixed id, editable title, who added it and when, and who removed it and when), and the text Gantry read out of it, in the browser, beside it in `sources/.text/`; a removed document keeps its manifest entry. On an Azure DevOps or GitHub workspace each upload, rename, text re-read and removal is one commit on the current Stage's branch, outside the stage Save, so a later Stage's branch (cut from it) carries the documents and `main` gets them when that Stage's Pull Request merges. _Avoid_: "reference document" (that is the Word style template a render pours text into); "asset" (an asset is an image the content *displays*; a source document is material the content is *drawn from*); "attachment".

**Interview instructions** (v0.13.0, being planned; `docs/adr/0062-interview-instructions-live-in-the-definition-and-only-add.md`): Text a Definition's author writes to steer how the AI interviews an architect, set optionally on the Definition, a Stage or a Module and stacked from broad to narrow. They add to Gantry's own interview rules and never override them, and they are versioned with the Definition. Written under `interview:` in a Definition, Stage or Module, and edited on a draft's Definitions page. _Avoid_: "prompt" (an implementation word); "guidance" (that is the per-Field key, which the AI also follows).

**Interview brief** (v0.13.0, #285; `docs/adr/0065-the-ai-interview-runs-on-pinned-grilling-and-domain-modeling-skills-with-standard-modules.md`; built by `web/lib/interviewBrief.js`): Everything the AI follows when it interviews an architect for one Stage, in precedence order: Gantry's interview rules, the bundled skills and their adapter, **Interview instructions** (Definition, then Stage, then Module), the Stage's purpose, Gate and the Artefact aimed for, each Field in scope (guidance, word budget at the Instance's Target size, whether the Gate requires it, type and options), the saved content of every Module (read-only ones included), the Glossary's preferred terms and logged term choices, the **Source documents**, and the **Decisions log** so far. The Source documents go in whole as a stable prefix while the pack is at most about half the model's context window, and as a catalogue when it is larger; everything that changes turn by turn comes after them so the prefix can be cached. The example Instance is never sent. One builder serves the in-app AI and, later, an **outside agent**. _Avoid_: "prompt" (an implementation word; the brief is also what an outside agent is told); "system message".

**Interview rules** (v0.13.0, #285; `web/lib/interviewRules.js`): Gantry's fixed rules for how the AI interviews: draft first; where every fact comes from (cite with `source:`, the architect's facts plainly, an accepted proposal marked "(target assumption)", nothing invented); saved content (and, on a remote workspace, **approved content** of an earlier approved Stage) changes only through a card; select Fields offer only the Definition's options; when a Field is done and a Stage is ready; and "Finish with your recommendations". Nothing overrides them: the bundled skills rank below them and Interview instructions only add. Shown read-only, with the skill versions, beside the Interview instructions editor. _Avoid_: "system prompt"; "guardrails".

**Interview skills** (v0.13.0, #285; `web/interview-skills/`, pinned in `web/lib/interviewSkills.js`): Matt Pocock's `grilling` and `domain-modeling` skills (MIT), bundled unchanged at a pinned release with their licence and credit, and mapped onto Gantry's terms by the **adapter** (`web/lib/interviewAdapter.js`): `CONTEXT.md` is the Glossary standard module, an ADR is a Key decision, looking a fact up is reading the Source documents, AskUserQuestion is question cards, and the shared-understanding check is the stage-end card. The adapter also lists each known clash with a rule and how Gantry settles it. A Gantry release moves to a newer skills release on purpose, with a CHANGELOG line; `tests/interviewAdapter.test.js` fails when the new text uses a term the adapter doesn't map. _Avoid_: "plugin"; "prompt template".

**Draft ahead** (v0.13.0, #296; `docs/adr/0063-drafting-ahead-approvals-in-stage-order-shared-modules-wait.md`; `web/lib/draftAhead.js`, `lib/draftAheadGuard.js`): The AI interview carrying on with a later stage of a remote Instance while an earlier stage awaits approval. It works only on modules no pending stage uses — the stage's **head start** — and extends shared modules once the earlier stage merges. A later stage that is ready while an earlier one is pending has its approval **queued**, never requested out of stage order. Gantry enforces the **head start** rule itself: while the Instance's current stage has its Pull Request open, a write to a module that stage (or another pending stage) can also edit is refused with a 400 (`code: shared-module-pending`), on both module-write routes and so over MCP; the Interview page shows such modules as **held** and the AI treats them as read-only. When nothing draftable is left, the **Waiting card** offers **Check approval now** (recommended) or **Stop here**; both save the head start as one commit on that stage's branch (status block state `head-start`), and **Check approval now** then runs Check status and, if the earlier stage merged, tells the AI the held modules are open. A stage can have more than one AI Save: the status block's `saves` lists each. The **run plan** gains **Drafting ahead** (the page's stage is ahead of the Instance's) and **Waiting for approval** (the Waiting card, or a stage holding a saved head start). _Avoid_: "skip ahead" (stages are never skipped); treating a drafted-ahead stage as approved or as able to pass its gate before the earlier one.

**Citation (of a Source document)** (#281, v0.13.0, being planned): A Markdown link in module content whose address is `source:<id>`, the id being the Source document's fixed id: `[Client brief, p. 4](source:client-brief)`. The words are the author's. In the editor it opens the document (a removed one keeps its words, marked "(removed)", and links nowhere; an id the Instance doesn't list is marked "(not found)"). The Word render prints it as plain "(Client brief, p. 4)" with no hyperlink, because readers usually have no repo access; the exported `.md` keeps the link as written. Only a link is a citation: an image, a code span and a fenced block are not. Shared by the compile step, the editor and the Local Workspace render request in `web/lib/sourceCitations.js`. _Avoid_: "reference" or "footnote" (it isn't numbered or collected where it is cited); "link to the document" (the Word reader gets no link).

**Sources appendix** (#281, v0.13.0, being planned): An Artefact's closing list of the Source documents it cites, switched on by the Definition with `source-appendix: true` on the Artefact (the "Sources appendix" checkbox on the Definitions page; default off, like `diagram-captions`; any value but `true` or `false` is an `invalid-source-appendix` problem). Rendered, in Word and in the exported `.md`, as a "Sources" section holding a table (title, original filename, date added; for a document with an **origin**, #318, its address and "retrieved <date>" instead) of only the documents that Artefact cites, in the order first cited, each removed one still listed and marked "(removed)". An Artefact that cites nothing has no Sources section. A Local Workspace's render request carries just the manifest entries of the cited documents, never a document or its text. _Avoid_: "bibliography" or "references" (it lists documents, not every source the content draws on).

**Origin (of a Source document)** (#318, v0.14.0; `docs/adr/0071-a-source-document-can-be-fetched-from-a-web-address-by-the-server-as-a-snapshot.md`; `web/lib/sourceDocuments.js`, `lib/sourceFetch.js`): Where a Source document added from a web address came from, kept on its `sources/manifest.yaml` entry as `origin: { address, finalAddress, fetchedAt }`: the address given, the final address after redirects, and when it was fetched. An entry without one is an upload and behaves exactly as before. The Gantry server fetches the address (`POST /api/sources/fetch`, which stores nothing) and the document is then stored through the ordinary add-document paths, in the browser's own folder for a Local Workspace. Private, loopback and cloud-metadata addresses are refused at every redirect hop by the check the AI relay uses (`lib/addressCheck.js`), with the Source documents' own operator override `GANTRY_SOURCE_FETCH_ALLOW_PRIVATE_URLS`, separate from the relay's; the operator's off switch is `GANTRY_SOURCE_FETCH_DISABLED`. Never a credential for another site: a page behind a sign-in is saved as a PDF and uploaded instead. _Avoid_: "link" or "bookmark" (the document is a snapshot, not a live link); "source URL" for the document itself.

**Fetch again** (#318, v0.14.0; `docs/adr/0071`): The architect's (or an outside agent's) manual refetch of a Source document that has an **origin**, from the address it was added from. Identical bytes add and flag nothing, and the panel says "unchanged since <date>"; different bytes are added as a new document that **replaces** the old one under its title, so the Fields that drew on the old one are flagged **Out of date**. Nothing refetches on its own. Only the newest copy is fetched again, in the app and over MCP alike, so a page keeps one line of replacements. On an Azure DevOps or GitHub workspace it is one commit when the page changed and none when it didn't. _Avoid_: "refresh" or "sync" (both suggest it happens by itself); "Extract text again" (that reads the kept copy again, not the address).

**Use as image** (#281, v0.13.0, being planned): Copies a PNG or JPEG Source document into the Instance's Assets as a new Asset (server workspace: `POST /api/instance/sources/:id/as-asset`, an Asset whose source is `sources/<file>`; Local Workspace, and Azure DevOps and GitHub (one commit on the current Stage's branch): a new file in `assets/` with a name safe to type). The copy is independent: it keeps no link back, so removing either never affects the other. _Avoid_: "convert" or "promote" (the Source document stays as it was).

**Interview page** (v0.13.0, #286; `docs/adr/0065-the-ai-interview-runs-on-pinned-grilling-and-domain-modeling-skills-with-standard-modules.md`; `web/lib/interviewView.js`): The full-page screen where the **AI interview** happens, opened with "✦ AI interview" in the Instance editor's header (the editor route with `?interview=1`, so it shares the editor's Save). Layout B of #243: the Source documents in a left rail with "+ Add Source document", the conversation in the centre (the kickoff form first, then the chat, with the free-chat composer pinned at the bottom), and a live draft preview of the Stage's Modules on the right. It works on the current Stage of a local, server, Azure DevOps or GitHub workspace Instance. The kickoff picks an AI Provider (the Default is pre-selected; an untested one is tested on Start) and, where more than one Artefact can pass the Gate, the Artefact to aim for (the lightest is pre-selected). _Avoid_: "wizard"; "chat page" (the chat is one column of three).

**Run** / **Run until** / **Run plan** (v0.13.0, #293; `web/lib/interviewRun.js`; local and server workspaces, which have no approvals; the remote case is **Draft ahead**): One AI interview carried across Stages. **Run until** is the picker at the **Interview page**'s kickoff that sets the run's target Stage (this Stage, or any later one; this Stage only by default). The **run plan** is the left rail's one row per Stage with its state: **drafting**, **awaiting confirmation** (its stage-end card is up), **waiting**, **done** and **paused**, the target marked, and Stages after the target struck through. On every Stage but the target the **stage-end card** has **Save, advance, carry on** (recommended: one stage Save, advance the Instance to the next Stage, and the AI starts that Stage by itself with the same AI Provider and the lightest Artefact) and **Save and stop here** (Save and pause); the target Stage's card is **Save and finish the run**. Stages are drafted in order and never skipped; the run is **done** when the target Stage's card is confirmed, with the Instance left at the target. Each Stage keeps its own **Decisions log**, and its status block records the run's target and each Stage's state, so a paused run (or one left between Stages) is found on the next visit and offered as **Resume the run**. If the advance is refused the Save stands and the run stays paused on that Stage. _Avoid_: "skip ahead" or running Stages out of order; "session" for the whole run (each Stage's interview is its own session with its own log).

**Hand edit** (v0.13.0, #289; `docs/adr/0064-the-decisions-log-is-per-stage-append-only-and-keeps-the-architects-words.md`; `web/lib/interviewSession.js`, `web/lib/interviewView.js`): The architect's own edit of a drafted Field, made in place in the **Interview page**'s live draft preview (click the Field). The Instance editor keeps showing saved content only, with a banner on a Module that has unsaved AI drafts pointing to the Interview page. A hand-edited Field is the architect's: Gantry's per-Field check (`checkDraft`) doesn't run on the text, the Field is done when it has content, the AI changes it only through a keep / use the AI's version / merge card (the **saved content** rule, with the architect's text standing in for the saved text), and the edit is logged as a `hand-edit` **Decisions log** entry keeping the typed text. The Field's `fields` record in the log is rebuilt from the edited text: the Source documents it still cites, plus the hand edit. Handing a Field back needs no button: the architect asks in free chat (the AI logs the request as a fact, and Gantry accepts a draft of the Field only after that) or chooses the AI's version on the card. A Field the AI is drafting at that moment shows "drafting…" and can't be edited. _Avoid_: "manual override"; "locking" a Field (the AI is asked, not blocked: the architect can always hand it back).

**Awaiting approval** / **Approval queued** (v0.13.0, #295; `docs/adr/0063-drafting-ahead-approvals-in-stage-order-shared-modules-wait.md`; `web/lib/interviewApproval.js`, `lib/approvalQueue.js`; Azure DevOps and GitHub workspaces): The two **run plan** states of a **run** on a remote workspace, where a Stage moves on only when its Pull Request merges. On the stage-end card the first choice is **Save, request approval, draft ahead**: one stage Save (the **Decisions log** committed with it on the Stage's own branch), then Request approval; the Stage's row then says **Awaiting approval** and links to its Pull Request, and the session waits. (The session then drafts ahead on the next Stage, #296.) A Stage that is ready while an earlier one is pending is **Approval queued** instead: its status block says `approval-queued` and its Pull Request opens by itself in the Check status that sees the earlier Stage merge. Nothing polls (ADR-0014): **Check status** runs when the architect clicks an Awaiting-approval row or presses it on the card, and once when a session resumes, and **what the Provider says overrides the log**. The AI never passes the Gate and has no part in Request Review. _Avoid_: "pending" (a Pull Request is pending for its Owner; the Stage is awaiting approval); "auto-approve".

**AI draft** (v0.13.0, #286): Text the AI has written into a Field of the Interview page's preview that has not been saved. It is marked "AI draft · unsaved" and is dropped if the tab closes; it becomes an ordinary draft Module's content only when the architect confirms the stage-end card, which makes one stage Save and leaves the Modules `draft` (only a person marks one `agreed`). A Field that already holds saved content is never drafted over: the AI's version goes to the architect on a **Keep / Use the AI's version / Merge** card first (#287). _Avoid_: "suggestion" (a suggestion is an option on a card).

**Token usage** (v0.13.0, #294; `docs/adr/0064-the-decisions-log-is-per-stage-append-only-and-keeps-the-architects-words.md` as amended by #255; `web/lib/tokenUsage.js`): What the architect sees about the AI interview's size: **tokens**, never money, and no budgets or limits. The **Interview page**'s rail shows **This session** (the run so far: the Stages it already went through, from their committed **Decisions logs**, plus what this session has used) and **This stage**, each in words such as "610k tokens", and the **run plan** shows each started Stage's total; hovering shows input, cached and output tokens and the share of input read from cache ("72% of input read from cache"). Nothing per round and nothing in AI Provider settings. The figures are what each AI Provider reports, with *input* always meaning all the input (Anthropic reports its uncached part apart, so cache reads and writes are added back). The status block of the **Decisions log** keeps each model used on the Stage (AI Provider type and model) with its own input, cached and output tokens, so a run resumed in another browser keeps its totals. _Avoid_: any cost, price or budget wording; per-round figures.

**Prompt caching** (v0.13.0, #294; `web/lib/aiAdapters.js`): Always on, for one hour, with no setting, wherever the **AI Provider** supports it. The **Interview brief**'s stable part (up to and including the **Source documents**) is the start of the request and an Anthropic request (or an Anthropic model via OpenRouter) carries a one-hour cache point right after it; originals attached to the first message are covered by a second one. Where the AI Provider caches on its own (OpenAI), Gantry only keeps that part in the same order and bytes on every turn. _Avoid_: offering it as a setting; putting anything that changes from turn to turn before the Source documents.

**Catalogue (of Source documents)** (v0.13.0, #292; `web/lib/interviewSources.js`, `web/lib/interviewBrief.js`): What the AI is given in place of the Source documents' text when the pack's extracted text is more than about half the AI Provider's context window: each document's id, title, kind, size, page count and heading outline. With it goes the `read_source_document(id, range)` tool (a range is `pages 3-5`, `section: Heading` or `start-end` character offsets; one read returns at most 30,000 characters), or, for a model that doesn't use tools, a fenced `gantry-read` block. Every read is recorded as an **input** of the Fields drafted from it (with a fingerprint of the text read), alongside the documents a draft cites; it is the `fields` part of the decisions log. _Avoid_: "index" or "summary" (the catalogue holds none of the text); "retrieval" (there is no search, the AI names what to read).

**Read visually** (v0.13.0, #292): A per-PDF choice, `readVisually: true` on its `sources/manifest.yaml` entry and set from the Source documents list, that sends the PDF itself to the AI instead of its text, for a PDF whose diagrams or layout text extraction jumbles. It only applies to an AI Provider that takes PDFs (Anthropic, OpenAI, and OpenRouter through a model that reads images); elsewhere the PDF's text is used. A scanned PDF (one with no text layer) is sent as the PDF without the choice, and listed as unreadable where the AI Provider doesn't take PDFs. Pictures follow the same pattern: sent as they are to a model whose Test found it reads images, unreadable otherwise. _Avoid_: "OCR" (Gantry does no text recognition; the model looks at the original).

**Draft field step** (v0.13.0, #286, rules from #246; `web/lib/interviewDraft.js`): How the AI writes a Field: one `draft_field` tool call (or, for a model that doesn't use tools, a fenced `gantry-draft` block) naming `module.field` and the value. Gantry checks each draft before it reaches the preview: a select value is one of the `options`, the word count is within the Field's budget at the Instance's Target size, every figure is cited with `source:` or marked "(target assumption)" (a figure the architect typed in the interview needs neither), and a cited Source document exists. Problems go back to the AI once; whatever is left shows as a warning under the Field, never a block. The same check runs on every content write (#306, ADR-0067; `web/lib/fieldCheck.js` calls `checkDraft`, no second copy of the rules): `PUT /api/instance/modules`, and so MCP `update_instance_modules`, returns `fieldNotes` (`{ module, field, kind, message }` for a select value not exactly an option, an over-budget Field, an unsourced figure; `[]` when clean), in a session or not, and the save always succeeds. _Avoid_: "validation" (it never rejects).

**Round** (v0.13.0, #287; `web/lib/interviewRounds.js`): The set of **Question cards** the AI asks together: every question whose prerequisites are settled. The dependency tree (a card's `after`) decides what is ready; a card waiting on an unanswered one is held back and shown by itself once its prerequisite is answered. Gantry's priority order only sorts the cards within a round: Fields the Gate requires, then Source documents that disagree (a term card is one), then missing facts, then optional Fields. Cards show four at a time with Back and Next and the round is submitted together; the answers go back to the AI, which redrafts the Fields they feed. _Avoid_: "wizard step" or "page" (a page is four cards of a round).

**Keep / use the AI's version / merge card** (v0.13.0, #287): The card that is the only way saved content changes in the AI interview (ADR-0065, rule 3), whoever wrote the saved content. It shows the saved text beside the AI's version. Keep (the recommended choice) leaves it and stops the AI proposing again; Use the AI's version puts it in the preview as an unsaved **AI draft**; Merge lets the AI write one combined version, which its next draft of that Field supplies. Nothing is written until the architect saves the Stage. On an Azure DevOps or GitHub workspace the same card guards **approved content** (#300, below), worded as **Needs re-approval**. _Avoid_: "overwrite" or "conflict" (the Save check's Field-by-Field merge, ADR-0068, is a different thing).

**Approved content** / **Needs re-approval card** (v0.13.0, #300; `docs/adr/0069-a-later-stage-re-approves-the-earlier-stage-fields-it-changes.md`; `web/lib/interviewReapproval.js`; Azure DevOps and GitHub workspaces): In the **AI interview**, a Field that an earlier **approved** Stage's Artefacts print (an earlier Stage with its approval Pull Request recorded, before the current Stage), whether it holds text or is empty. The AI changes it only through the **Keep / Use the AI's version / Merge** card, worded **Needs re-approval**: it names the Stage ("printed by SOAP, which is already approved ... changing it changes approved content, so SOAP needs re-approval with this Stage") and shows the approved wording beside the AI's version; the choice is a `saved-content` **Decisions log** entry carrying `reapproves` (the Stages). Source-document carry-forward is held to the same rule because it goes through the same draft check. A Field only a later Artefact prints is not approved content. After a Save changes one, the earlier Stage's **run plan** row shows **changed since approval**; the stage-end card says the Save **re-renders** the earlier Stage's affected documents (`out/approved/` keeps the approved copy, #276) before it requests approval, and the Pull Request also re-approves that Stage (#275). A local or server workspace has no approved Stages and no such card. _Avoid_: "locked" Field (the architect can always choose the change); "frozen".

**Done** / **ready** (v0.13.0, #287; `web/lib/interviewReadiness.js`): A Field is **done** when it has content, sits between about 60% of its word budget and the budget, covers each point its guidance asks for (the AI lists any it has not in `uncovered`) and no open question feeds it. The Stage is **ready** when Gantry's real Gate check passes for the Artefact aimed for and every Field in scope is done, and only then does the stage-end card appear. A Field is in scope for this when the Gate requires it for the Artefact aimed for or it has content, saved or drafted; an optional Field the Source documents don't support stays empty and doesn't hold the Stage back. _Avoid_: "complete" (the Gate check's own word for a satisfied Artefact).

**Finish with your recommendations** (v0.13.0, #287): The button, always available on the Interview page, that accepts every pending recommendation on the open cards, has the AI redraft with each figure it proposed marked "(target assumption)" (Gantry marks it, not the model), then asks one last **Round** about only the Fields the AI cannot responsibly propose, such as a named Owner. The stage-end card waits for that round; the AI is not shown further cards afterwards. _Avoid_: "auto-complete" or "skip questions".

**Decisions log** (v0.13.0, #288; `docs/adr/0064-the-decisions-log-is-per-stage-append-only-and-keeps-the-architects-words.md`; `web/lib/decisionsLog.js`, `web/lib/interviewLog.js`, `lib/decisionsLog.js`): The record, kept with each Stage of an Instance as `interview/<stageId>.yaml` beside `modules/`, `sources/` and `assets/` in every workspace kind, of what the architect decided during the AI interview. It is committed in the same Save as the Stage's content (a Local workspace writes both through its folder; a server workspace takes the log as `decisions` in the body of `PUT /api/instance/modules`, and a Blob container writes both all-or-nothing). Three parts: a **status block** (one line per session: who, target Stage, state, Artefact, last AI save, each AI Provider type and model used with input, cached and output tokens, the Interview instructions version and the skill versions; built from known keys only, so never a key, an address or a custom name); **fields** (for each drafted Field, its inputs, each a Source document and range or an earlier-Stage Field with a fingerprint, and the ids of the entries that fed it; overwritten when the Field is redrafted); and **entries**, which are append-only: question cards answered (question, options, recommendation, why, cited document by id, the answer, the architect's own words from Other, the Field it fed), architect facts from free chat kept word for word (the AI names a quote with its `log_decision` tool and Gantry keeps the architect's whole message, refusing anything they did not type and any thanks or "go on"), keep / replace / merge choices on saved content, Save-clash choices (`save-clash`), **term choices** (#291), **hand edits** (#289: the architect edited a drafted Field in the Interview page's preview; the entry keeps the text they typed, and a later hand edit of the Field replaces it), open questions, the Artefact aimed for, a restart marker ("Start this stage over") and a change of model. A changed answer is a new entry with `replaces`, an open question is closed by one with `resolves`, nothing edits or deletes an entry, and a Save that would is refused (409, `append-only`). The AI's replies are never kept: there is no transcript. Shown read-only in the editor's **Decisions log panel** (latest answers, open questions highlighted with **Resume to answer**, history on request) and as a count in the **Interview page**'s rail; never in a rendered Artefact. An entry an **outside agent** recorded is labelled as such, because Gantry can't check its quote of the architect. It is the evidence for content the architect supplied, and what a paused session resumes from (see **Pause** and **Working copy**). When two sessions' logs have both moved on they merge in time order: a later answer to a question both answered gets a `replaces` link (or an earlier one a `replacedBy`, because an entry already in the log is never edited), and the `fields` section is rebuilt; a clash on a Save that the architect settled is a `save-clash` entry. _Avoid_: "transcript" or "chat history" (the AI's side of the conversation is not kept); "audit log" (it records design decisions, not who clicked what).

**Term choice** (v0.13.0, #291; `docs/adr/0065-the-ai-interview-runs-on-pinned-grilling-and-domain-modeling-skills-with-standard-modules.md`): The architect's answer to a **term card** (a Question card with `kind: term`), which the AI asks when Source documents name one thing differently, or when the architect's own wording (a card's "Other" text or free chat) is fuzzy or clashes with the Glossary. Each name is an option; the one chosen is the **preferred term** (or the architect's own wording, if they typed it) and the others become names to **avoid**. It is logged as a `term` entry in the **Decisions log** (a changed choice replaces the earlier one about the same thing) and binds every later Stage: the **Interview brief** gives each Stage the choices of the Stages before it. Where the Glossary standard module is mounted on the Stage, the AI drafts it from the choices (a row each: Preferred term | Definition | Avoid) and Gantry checks the draft carries every one; where it is not, the choice stays in the log. _Avoid_: writing a term into the Glossary the moment it is settled (the choice is logged and drafted at the Stage that mounts the Glossary).

**Standard module** (v0.13.0; `docs/adr/0065-the-ai-interview-runs-on-pinned-grilling-and-domain-modeling-skills-with-standard-modules.md`): A Module Gantry itself provides rather than a Definition — **Glossary**, **Open questions** and **Key decisions** — with a fixed id, Field shape and version. A Definition chooses which Stages mount it and which version, by listing it under `standard-modules:` and on a Stage like any Module, and may add guidance and Interview instructions to it, but cannot change its shape. A released version never changes: a Gantry release adds a new version beside it, so a published Definition renders the same forever. The Definitions page labels it **Gantry-provided**. _Avoid_: "built-in module" (it is never present unless a Definition mounts it); "shared module" (that is a Definition's own module mounted on several Stages).

**Key decision** (v0.13.0; `docs/adr/0065-the-ai-interview-runs-on-pinned-grilling-and-domain-modeling-skills-with-standard-modules.md`): A design decision significant enough to record in the Key decisions standard module — hard to reverse, surprising without its context, and the result of a real trade-off. Each has a number it is given once (`AD01`, `AD02`, …) and keeps when decisions are reordered or removed, and a removed number is not handed out again. A Definition mounts the module with a **prefix** (`design` keeps "AD"; "KD" if none) and a **Decision style**. Links between Key decisions are written by number. In `design` these are the **Architecture Decisions**. In the AI interview a Key decision is offered only where the module is mounted on the Stage, as a card with `kind: decision` that gives the three reasons it passed that test; a routine answer is an ordinary card and only enters the **Decisions log**. The AI drafts a confirmed one as the next number, in the mount's prefix and style, and Gantry checks the draft's prefix, parts, numbers and links (#291). _Avoid_: confusing it with an entry in the **Decisions log**, which records every answer given in the interview, significant or not.

**Decision style** (v0.13.0): How a Definition has its Key decisions written, chosen on the mount: **default** (title, context, decision, why, considered options, consequences) or **WH(Y)** (github.com/cgbarlow/adr: a title, the six-part statement "In the context of… facing… we decided for… and neglected… to achieve… accepting that…", and typed links to other Key decisions — depends on, supersedes, relates to). A Word render prints a WH(Y) decision as that one sentence, with its links under it. _Avoid_: "template" or "format" (a style changes how the one Field is written, not its shape).

**Replaced (Source document)** (v0.13.0, #297; `web/lib/sourceDocuments.js`): A Source document the architect has said a newer upload supersedes — "Client brief v3 replaces v2". Said at upload with the **"This replaces…"** picker, which records `replaces: <older id>` on the *newer* document's entry in `sources/manifest.yaml` (the older entry is untouched; "replaced by <new>" is worked out from the link, and the older document shows it). The older one is kept and still citable; it is never edited in place, because a newer version is always a document of its own. A document can only replace one that is still there, not a removed one. _Avoid_: "new version of" (there are no versions inside one document); "removed" (a removed document's file is gone; a replaced one stays).

**Out of date (Field)** (v0.13.0, #297; `docs/adr/0064`, `0068`; `web/lib/outOfDate.js`, `web/lib/outOfDateState.js`): A Field whose content drew on something that has since changed — a Source document **removed**, **replaced** or **re-extracted** (read again to a text that actually differs: `textChangedAt` in the manifest, set only when the text's fingerprint changed, so an identical re-read flags nothing), or an earlier Field the draft read that is no longer what it saw (usually because the Save check took the other side's version, ADR-0068) — and which the architect has not yet kept or redrafted. Exactly the Fields that drew on or cite the document are flagged: those the Stage's decisions log lists it as an input of (`fields` section), and any content, hand-written included, that cites it with `source:<id>`. Flags are not stored: they are worked out from the manifest, the decisions logs and the saved content on opening and after every Source document change and Save, the same in every workspace kind (where a Provider workspace has no readable decisions log yet, the citing content is what is flagged). A flag clears when the Field is drafted again after the change or when a decisions-log entry of kind `source-update` naming the document and the Field is made after it (**Bring up to date**'s cards write those; for a Field flagged because an earlier Field changed, the entry names that Field and the fingerprint of its text when answered, so a later change flags it again); Gantry flags, only the architect clears. Shown as the editor's banner ("4 Fields drew on Client brief, now replaced by Client brief v3: Bring up to date"), a mark on each Field and an "N Out of date" mark on each run-plan row. _Avoid_: "stale" in the UI (an engineering word); "invalid" (the content may still be right).

**New since last interview** (v0.13.0, #297): The mark on a live Source document uploaded after the last AI interview saved anything (the latest `lastAiSave` or Field draft time across the Stages' decisions logs) that **replaces nothing**. It flags no Field: it only tells the architect, and the next normal session (#298), that the document has not been read against what is saved. That session's AI reads it against the saved content and the decisions log, and asks a card only where it adds to or contradicts something. Nothing is marked until some interview has run. _Avoid_: "unprocessed"; "pending".

**Sent back** / **Revise a Stage** / **PR comment answered** (v0.13.0, #299, decided in #247; `docs/adr/0063`, `0064`, `0069`; `web/lib/prRevision.js`, `lib/pullRequestComments.js`; Azure DevOps and GitHub workspaces): What happens when the Owner does not approve the Pull Request of a Stage the AI interview saved: a **changes-requested** vote (GitHub's request changes, Azure DevOps's waiting for author) or a **rejection** (Azure DevOps's reject vote; on GitHub a Pull Request closed without merging). Check status (never polling) reports it, and one card asks **Revise <Stage> with the AI** or **Stop the session here**; **drafting ahead pauses** while it is up and **drafted-ahead work is kept either way** (saved as a head start on its own branch). **Revising** (`?interview=1&revise=1`) is a session on that Stage whose first act is reading **every comment on the Pull Request, resolved ones included** (a new Provider capability, `getPullRequestComments` on both clients, `GET /api/instance/pull-request-comments`; read-only), listing them in the conversation and asking **one card per comment** (Change the content / No change needed / Log an open question / Other) before the AI is called. Each answer is a **PR comment answered** entry in the **Decisions log** (author, link, excerpt, the outcome and the ids of the entries that answered it). The AI redrafts only what was chosen, saved content changes only through keep / use the AI's version / merge, and **Save the revision** is one Stage Save on the Stage's own branch that updates the open Pull Request; the row goes back to **Awaiting approval** (a revising Stage's row says **revising**) and the architect tells the Owner. **The AI never writes to the Pull Request**: no comments, replies or resolved threads. It is also never told who wrote a comment (the names stay in the log, as for a Reviewed copy, `docs/adr/0066`). After the revision, Gantry finds later-Stage Fields drafted from content that changed (by fingerprint, `staleLaterFields`) and a **Bring up to date** round on that Stage asks keep / redraft for each; it keeps the Stage's approval-queued or head-start status. _Avoid_: the AI replying to or resolving a comment; treating a resolved thread as not worth asking about (it is asked, recommending no change); advancing a Stage whose Pull Request was sent back.

**Re-open offer** (v0.13.0, #299; `docs/adr/0026-reopen-signed-off-stage.md`; `web/lib/prRevision.js`, `web/lib/interviewSession.js`): The AI interview's way of re-opening a signed-off Stage when a **Source document** contradicts approved content or the architect asks: an `ask_architect` card of `kind: "reopen"` naming the Stage (no options needed). Gantry makes it a **Re-open <Stage> / Not now** card **only when ADR-0026 would allow it right then** (the Stage just before the current one, no later Stage with a branch); the brief lists which Stages qualify. Otherwise there is no card: an **open question** naming the blocker goes in the Decisions log. A re-opened Stage joins the run plan, its page starts by itself and its log carries on in the same file. _Avoid_: offering a re-open Gantry would refuse; re-opening a Stage silently.

**Bring up to date** (v0.13.0, #298, decided in #249; `docs/adr/0063`, `0064`, `0069`; `web/lib/bringUpToDate.js`): The round of question cards about exactly the Fields flagged **Out of date**, one card per Field, asked before the AI is called. Three ways in: the editor banner's **Bring up to date** (the Interview page on just those Fields, with no run, Artefact or "Run until", stage by stage in order), the start of any normal interview that has flags waiting, and, for **New since last interview** documents, the AI's read of them against saved content at the start of a normal session. A changed, replaced or re-read document: **Keep** or **Redraft**; a removed one: **Keep** (the citation shows "removed"), **Re-cite** to another document (pre-selected when one supports the content: its replacement, or a document the Field already drew on or cites; Gantry rewrites the citations itself) or **Redraft without it**; a Field flagged for an earlier Field that changed: Keep or Redraft with Keep recommended. A redraft of saved content still goes through keep / use the AI's version / merge. Each answer is a `source-update` entry naming the triggering document; only an answer clears a flag. **Where the change lands:** in place on a Local or Server-hosted workspace (any Stage, in order); on Azure DevOps and GitHub, a Field of an approved Stage is **carried forward** to the current Stage where its Module is editable (it changes approved content, so it is re-approved with the current Stage, ADR-0069), else the card offers a **re-open** (ADR-0026: only the Stage just before the current one, and only while the current Stage has no branch, which a Source document change or any Save creates; choosing it ends the round with a choice between re-opening now, which drops the round's other unsaved answers because saving them would start the current Stage, and saving them instead), else it logs an **open question** naming the blocker; a Stage awaiting approval takes the change on its own branch, updating its Pull Request; a drafted-ahead Stage is never touched. Accepting a change to an `agreed` Module returns it to `draft` and the log keeps a `returned-to-draft` note saying why. _Avoid_: "refresh" and "sync" (nothing changes without an answer); "update the Instance" (a round changes only the flagged Fields).

**Pause** (v0.13.0, #290; `docs/adr/0064-the-decisions-log-is-per-stage-append-only-and-keeps-the-architects-words.md`; `web/lib/interviewView.js`, `web/lib/interviewResume.js`): The button on the Interview page that saves the decisions log and the drafts so far as one Save (through the Save check) and ends the run with its status line set to `paused`. It is a Save only because the architect asked, so "no autosave" holds, and the Modules stay `draft`. The Stage then **resumes** in this browser or any other: opening the Interview page on a Stage whose log has decisions shows a recap ("Resuming Shape: 14 decisions, 2 open questions, last asked about hosting"), the AI is given the log and the saved content rather than the old conversation, and the paused session of the same architect is taken over so the log keeps one status line for it. On a workspace with a Provider, Check status runs once first and what it reports overrides the log's status block. _Avoid_: "autosave", "session restore" (the conversation is not kept).

**Working copy** (v0.13.0, #290; `web/lib/interviewWorkingCopy.js`): What the browser keeps of an unsaved AI interview between Saves: the drafts, the entries not yet committed, the open round of cards and the AI's side of the history it needs to carry on. The same browser resumes exactly from it. It is never the truth: if the committed log has moved on since the copy began (another browser of the same architect, or another session, saved), the committed log wins and the copy is **set aside** with a notice. It holds no key (an AI Provider is referred to by its id in that browser). A browser that blocks storage simply has none. _Avoid_: "draft" (a draft is the AI's unsaved Field content, which the copy also holds).

**Reviewed copy** (v0.13.0, being planned; `docs/adr/0066-reviewed-copies-come-back-as-a-focused-interview-round.md`): A Word document Gantry rendered that comes back carrying someone's comments and tracked changes, brought into Gantry so the AI can work through the feedback with the architect. It is kept with the Instance as the record of what came back, but it is not a Source document and is never cited. Only Gantry's own tagged renders are accepted. Brought in with **Bring in review comments** in the editor header (#302): `web/lib/reviewedCopy.js` reads the Word XML in the browser (threads with replies and a resolved flag, tracked changes, and the Field bookmarks each overlaps), refuses a document with no `gantry-*` properties or from another Instance or Artefact, and keeps each accepted copy as `reviews/<id>.docx` with an entry in `reviews/manifest.yaml` (fixed id, Artefact, Stage, render id and commit, commenters, date, comments answered): one commit on the current Stage's branch for a Workspace-backed Instance, one write for a server or Local workspace, 25 MB per upload. A copy that lost its Field bookmarks (Google Docs) has its comments placed by matching text against the content the render came from — rebuilt from `gantry-commit`, or today's content where there is no history — and says so; the editor's **Review comments** panel lists each copy's threads by Field, read-only. Working through them is the **Review round** (#303). _Avoid_: calling the person who commented a "reviewer" without qualification — say **commenter**, to keep them apart from the **Request Review** reviewer and the Pull Request's sign-off reviewer, even when it is the same person; "returned document" or "review document".

**Tagged render** / **Field bookmark** / **Render properties** (v0.13.0, #301; `docs/adr/0066-reviewed-copies-come-back-as-a-focused-interview-round.md`, implemented in `lib/wordFieldTags.js`): Every Word render is tagged so a **Reviewed copy** can be read back onto Fields. Each printed Field's value sits inside an invisible **Field bookmark** named `gf_` plus eight hex digits of a hash of `module/field` (`fieldBookmarkName`; a Field printed a second time gets `_2`, and so on), and the document carries `gantry-*` **Render properties** (File > Properties > Custom): `gantry-instance`, `gantry-artefact`, `gantry-stage`, `gantry-definition` (`id@version`), `gantry-commit` (the full hash of the commit the content was at; absent on a server workspace, which has no history) and `gantry-render-id` (new on every render). Gantry tags while compiling the Word conversion only (templates read a view of the Modules with the same values, so conditions, the Filename pattern and the cover see plain values), so no Definition or template changes and the exported `.md` is untouched; both the native Pandoc and the browser's pandoc-wasm convert the same tagged Markdown. A value that cannot be wrapped without changing how the Markdown reads (for example a list that sits against another list) is bookmarked with raw OpenXML instead of a Pandoc Div, so the visible document never changes. _Avoid_: asking a Definition author to mark Fields up; matching a returned document by its bytes or hash (SharePoint rewrites the file), only by the properties.

**Review round** (v0.13.0, #303; `docs/adr/0066-reviewed-copies-come-back-as-a-focused-interview-round.md`; `web/lib/reviewRound.js`, `web/lib/reviewView.js`, `web/lib/interviewSession.js`): The Interview page working through a **Reviewed copy**'s comments with the architect, as question cards: **Work through review comments** in the rail (or the editor's Review comments panel) opens a focused round, `?interview=1&review=1`, with no run and no Artefact; if an interview is going, paused, or about to start, the review questions **join its next round** instead. One card for each unresolved thread; one commenter's tracked changes in one Field are one card; commenters who changed the same wording differently share one; threads resolved in Word are listed collapsed and can be reopened. The choices are **Accept the edit** (recommended only when the Field is unchanged since the render; Gantry makes it itself when it can do so without guessing, else the AI does), **Revise** (the AI's draft meets the keep / use / merge card), **Keep as is** (with the architect's own words) and **Can't settle yet** (an open question); comments on the cover, Document Control, table of contents or no Field get **Assign to a Field**, **Log an open question** or **Note it**. The AI is told commenters as "Reviewer 1", "Reviewer 2" and never sees a real name (`scrubNames`); the real names stay in the Reviewed copy, the manifest and the log. Each answered thread appends a **review-answered** entry to the Stage's **Decisions log**, and the manifest's answered count follows. Where a change lands follows **Bring up to date**; a drafted-ahead Stage never takes one, and an accepted change to an `agreed` Module returns it to `draft` (the card says so first). _Avoid_: "review session" (it is a round, not a "run until" session).

**Review response list** (v0.13.0, #304; `docs/adr/0066-reviewed-copies-come-back-as-a-focused-interview-round.md`, implemented in `web/lib/reviewResponse.js`): The table Gantry builds from the decisions log after a Reviewed copy has been worked through, as a Word document the architect downloads and sends back themselves. One table for each Reviewed copy, one row for each answered thread (`review-answered` entry, the latest answer standing): the comment (with replies and the tracked change word for word), the commenter, the Field, the outcome in plain words (*Edit accepted*, *Wording revised*, *Kept as it was*, *Not settled yet*, *Noted*, *Taken up*) and the architect's reason as they typed it (a dash where they gave none: Gantry does not invent one). A revision whose AI draft the architect then did not take (a later `saved-content` entry that kept what was saved) reads *Looked at; the wording stayed as it was*, so the list never claims a change that was not made. It is generated in the browser on demand (Interview page rail, the card after a Save, the editor's Review comments panel) and never stored: not written into the Reviewed copy, not added to the Instance's files, not committed. The card after a Save also nudges the architect to render again (ADR-0034); Gantry does not. _Avoid_: "comment resolution" (nothing is resolved in the commenter's document); replying to or editing the Reviewed copy.

**Outside agent** (v0.13.0, #305 and #307; `docs/adr/0067-outside-agents-get-the-whole-ai-interview-over-mcp-held-to-the-in-app-ais-rules.md`): An AI agent outside Gantry, such as Claude Code, working on an Instance through the **Gantry MCP server**. It can do everything the AI interview does, including driving an interview session, and it is held to the same rules as Gantry's own AI while it does. It is its own AI, so it uses no **AI Provider**. Over MCP (#305) it lists and reads **Source documents** (the committed extracted text a page at a time, a picture as a picture), each Stage's **Decisions log** and **Reviewed copies** with their threads by Field, uploads a Source document or a Reviewed copy under the browser's rules (with no browser, `gantry serve` runs the same extractors), and sees **Out of date** Fields in `get_instance`. It can also run an interview session (#307): `get_interview_brief` returns the **Interview brief** the in-app AI gets (built by the same `buildInterviewBrief`) plus a recap of the Stage's log, and `start_interview_session`, `pause_interview_session` and `resume_interview_session` give it a "run until stage X" session that moves between the browser and an outside agent through the last commit (whichever side resumes runs Check status once and recaps, and the committed log wins). In a session `update_instance_modules` takes the **session**, **entries** and the stage version (required), and commits them with the content in one commit; Gantry stamps each entry **recorded by an outside agent**, names "outside agent" and the model the agent reports in the session status (tokens "not reported"), and rebuilds the log's `fields` section from the content's citations and the entries that name each Field. Gantry itself refuses an agent in a session what it refuses its own AI, with the same reasons: passing a Gate (`advance_stage`), approvals out of Stage order and writes to a shared Module while an earlier Stage's Pull Request is open (`lib/outsideAgentSession.js`); outside a session nothing new is refused. _Avoid_: "external AI" or "MCP AI"; calling it an AI Provider (an AI Provider is a service Gantry calls; an outside agent calls Gantry).

**Asset ("Image" in the UI)**: An uploaded binary referenced from markdown as `![name](asset:<id>)`. "Image" is the UI label for the toolbar action that inserts an asset reference. _Avoid_: renaming stored references to `image:` or treating "Image" as a concept distinct from Asset

**Diagram caption** (#195, `docs/adr/0053-diagram-captions-on-the-fence-and-in-alt-text.md`): The title an author gives a diagram, rendered in the Word document as `Diagram N. <title>` directly under the figure and kept on the same page. Only in an Artefact whose Definition opts in with `diagram-captions: true` (the Artefact's "Diagram captions" checkbox on the Definitions page; every design v3 Artefact does); every other Artefact renders its diagrams exactly as before, and a value other than `true` or `false` is an `invalid-diagram-captions` problem. A Mermaid block is captioned on its fence, `` ```mermaid {caption="Security architecture"} ``. An image is captioned by its alt text, `![Security architecture](asset:<id>)`, and only when it stands alone in its paragraph. Mermaid blocks and images share one numbering sequence per rendered document, assigned by the compile step, so every render path uses the same numbers. The caption is also the picture's alt text. The exported `.md` keeps the caption syntax as written, and the editor shows the title without a number, because a field is not a document. An uncaptioned Mermaid block is still labelled plain "Diagram N"; an image with no alt text gets no caption and no number. _Avoid_: typing "Diagram 3." into a caption yourself (the number is added for you and would appear twice); a separate caption paragraph under the diagram (it reads as body text and drifts away from the figure); "figure" or "figure title" for this (the document calls them diagrams)

**Save (stage Save)**: The one action that stores the author's edits — every module on the viewed stage whose content differs from what's saved, in one go. A module has **unsaved changes** while its fields or section layout differ from its saved content (a comparison, not an edit flag: undoing back to the saved text means no unsaved changes). Leaving the stage, or running Render, Advance or sign-off, with unsaved changes asks Save / Discard / Cancel. On a Workspace-backed instance one Save is one commit on the stage branch; saving never renders an artefact — only Render does. A Save first checks the **Stage version** and settles any **Clash** Field by Field, so it never overwrites someone else's save silently (`docs/adr/0068-every-stage-save-checks-what-changed-since-it-was-read-field-by-field.md`). _Avoid_: "autosave" (deliberately not a thing); per-module save.

**Stage version** (#270, `docs/adr/0068-every-stage-save-checks-what-changed-since-it-was-read-field-by-field.md`): A fingerprint of a Stage's content — every Field of every Module the Stage mounts, with each Module's status and owner — noted when the editor opens the Stage and compared again before every Save. The same in every workspace kind (local, server, GitHub, Azure DevOps), and returned by reading an Instance (`stageVersion`; MCP `get_instance` returns it and `update_instance_modules` takes it back as `stageVersion`, refusing a stale one with the Fields that differ, #272). It follows Fields only: an Asset upload, a rendered document or any other commit that changed no Field leaves it as it was, so raises no Clash. _Avoid_: "revision" or "commit id" (a commit that changes no Field does not change the Stage version); "etag".

**Clash**: What a Save finds when the Stage version has changed since the editor read it — someone else saved meanwhile. Gantry settles it Field by Field, three ways, between what the saver started from, what is saved now and what the saver has: only the saved side changed, so theirs is taken; only the saver changed it, so theirs is kept; both changed it, so a dialog shows both versions to pick or edit. Nothing is overwritten silently. _Avoid_: "conflict" in the UI (that word already means a Git merge conflict on a stage-branch sync); settling a Clash for the whole Stage at once (taking theirs would lose every unsaved answer).

**View mode (Visual / Split / Markdown)**: How a module's markdown fields are displayed and edited on the editor screen — one setting for the whole screen, chosen from the **Mode** dropdown. **Visual** (the default) is a Word/Loop-style editing surface over the content; **Split** shows the raw text and Visual side by side over the same content, each live; **Markdown** edits the raw text. All three are first-class peers — none is an "advanced" escape hatch — and share one undo history. Visual's bar is content parity with Markdown (including Loop-style tables: type in cells, Tab between them, add, remove and move rows and columns, align columns, delete the table) — never features markdown can't store (merged cells, colours, column widths). Images show in place with the *Source* citation staying automatic; a Mermaid diagram shows drawn and is edited as text in a pop-over; Insert → Section/List stay module-level actions outside the editor. Whatever the view, an untouched field must save back unchanged and an edit may tidy only what it touched, because stage content is reviewed as a Pull Request diff. An archived instance is read-only in every view. _Avoid_: "Rendered" for any editor view (reserve "rendered" for generated Word/Excel artefacts); treating Visual as a way to store anything the markdown file can't
