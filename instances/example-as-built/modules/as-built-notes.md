## Business process flows

**Certificate submission (happy path):**

1. Provider navigates to `provider-portal.contoso.com` and selects "Submit a Disability Allowance certificate."
2. Provider authenticates via redirect to the external provider-authentication service (OIDC). On success, the service posts back an `id_token` containing the provider's registration number.
3. Provider enters the client's one-time reference code (8 characters, format `NNNN-NNNN`). The portal calls `GET /reference-codes/{code}` on the Intake API, which validates the checksum digit (last character, Luhn mod 10 over the preceding 7) and returns the client's masked name (e.g. `J*** S***`) and date of birth (month/year only) for the provider to confirm.
4. Provider confirms the masked identity matches who they're submitting for, then uploads the certificate (PDF or JPEG, max 10MB).
5. Portal calls `POST /certificates` on the Intake API with the reference code, provider registration number, and the file as a multipart body.
6. Intake API validates the file (MIME sniffing, not just extension — see Detailed technical design), stores it in the certificates S3 bucket, and calls EOS's `create-application-document` endpoint to attach it to the client's existing application.
7. Portal shows the provider a confirmation screen with a submission ID. No further provider-facing status tracking exists in this release — EOS case owners see the attached document through their existing EOS workflow.

**Reference code mismatch path:** if the checksum fails or the code isn't found, the portal shows a generic "We couldn't find that reference — check the code and try again" message. It deliberately does not distinguish "wrong checksum" from "not found," to avoid giving a scanning attacker a signal about which codes are valid.

**Provider not yet registered path:** the external provider-authentication service handles registration entirely outside this system; an unregistered provider is bounced back to that service's own sign-up flow and never reaches the portal's own screens.

## Detailed technical design

**Provider Portal** (new, `provider-portal` repo): server-rendered Node.js/Express app, no client-side framework. Routes: `GET /` (landing), `GET /auth/callback` (OIDC redirect target), `GET /submit` (reference-code entry, session-gated on a valid OIDC session), `POST /submit/confirm` (masked-identity confirmation), `POST /submit/upload` (file upload + submission). Session state (post-auth, pre-submission) is held server-side in Redis, keyed by a signed cookie, 15-minute TTL — nothing about the client is ever sent to the provider's browser beyond the masked name/DOB already described.

**Intake API** (new, `intake-api` repo): stateless REST API, Node.js/Express, internal-only (no public route). Endpoints:
- `GET /reference-codes/{code}` — validates checksum, looks up the code in the `reference_codes` table (Postgres, existing EOS-adjacent database, new table added via migration `007_reference_codes.sql`), returns masked identity or 404.
- `POST /certificates` — validates file (see below), streams to S3, calls EOS internal API `POST /internal/applications/{id}/documents`.

**File validation logic:** accepts `Content-Type: application/pdf` or `image/jpeg` from the multipart header, then independently verifies via magic-byte sniffing (`%PDF-` for PDF, `\xFF\xD8\xFF` for JPEG) — the declared `Content-Type` is never trusted alone. Files failing the magic-byte check are rejected with a 422 before anything is written to S3. Max size enforced at 10MB via Express's body-parser limit, returning 413 above that.

**Reference code checksum:** 7 random digits (from a cryptographically secure RNG, not `Math.random`) plus a Luhn mod-10 check digit as the 8th character, formatted `NNNN-NNNN` for display. Codes are generated by EOS when a Disability Allowance application is created and pushed to the `reference_codes` table via an existing EOS-to-Postgres sync job (`eos-sync`, runs every 5 minutes) — the Provider Portal system never generates codes itself.

**UI wireframes:** the submit flow is 3 screens — reference-code entry (single text input, auto-formats as `NNNN-NNNN` while typing), identity confirmation (masked name/DOB + Yes/No), file upload (drag-and-drop zone + browse button, single file only). No wireframe images are attached to this document; the live implementation in the `provider-portal` repo's `views/` directory (server-rendered EJS templates) is the source of truth for exact layout.

## Infrastructure and configuration

Hosted in the existing Contoso AWS landing zone (account `contoso-prod-govt`, `ap-southeast-2`).

**Provider Portal** (public zone, VPC `vpc-0a1b2c3d`, subnet `subnet-public-a` 10.20.1.0/24): ECS Fargate service, 2 tasks, behind an internal ALB (`provider-portal-alb`, `10.20.1.40`) which itself sits behind the existing Contoso API Gateway (no new public IP — routed via the Gateway's existing `*.contoso.com` wildcard cert). Container port `3000`, health check `GET /healthz`.

**Intake API** (private zone, subnet `subnet-private-a` 10.20.2.0/24, no internet route): ECS Fargate service, 2 tasks, internal ALB `intake-api-alb` at `10.20.2.30`, container port `4000`. Security group `sg-intake-api` allows inbound `4000` only from `sg-provider-portal` (Provider Portal's security group) — nothing else can reach it.

**Reference codes database:** existing shared Postgres instance `eos-postgres-prod.internal` (`10.20.3.10:5432`), new schema `intake`, table `intake.reference_codes`. Connection via IAM-authenticated RDS proxy, no static credentials in either service's config.

**Certificates S3 bucket:** `contoso-provider-portal-certs-prod`, `ap-southeast-2`, server-side encryption with the existing Contoso-managed KMS key `alias/contoso-shared-docs`, versioning enabled, no public access (bucket policy denies all non-VPC-endpoint traffic). Accessed by the Intake API only, via VPC endpoint `vpce-0f1e2d3c`.

**Redis session store:** ElastiCache Redis, cluster `provider-portal-sessions`, `10.20.1.50:6379`, single node (no HA — acceptable given sessions are 15-minute, re-derivable by re-authenticating).

**DNS/environments:** production `provider-portal.contoso.com` → API Gateway → ALB `10.20.1.40`; staging `provider-portal.staging.contoso.com`; development `provider-portal.dev.contoso.com` (matches the environments listed in this solution's SAD/SSAD `integration` module — same three environments, no additional ones were added during build).

**Secrets:** OIDC client secret, RDS proxy IAM role ARN, and S3 bucket name are all injected via ECS task definition environment variables sourced from AWS Secrets Manager (`provider-portal/prod/*`) — never committed to either repo.

## Changes from the agreed design

Two deviations from the architecture/integration modules agreed at Build Readiness Confirmed:

1. **Reference-code generation moved out of scope during build.** The SAD's architecture module implied the Intake API might need to generate reference codes; in practice EOS already had a code-generation capability from an unrelated prior initiative, so the existing `eos-sync` job was extended instead of building a second generator. Net simpler, no new component.
2. **Session store added.** The original design didn't call out session state explicitly. Once the identity-confirmation step (masked name/DOB) was built, it became clear that state needed to persist between the reference-code screen and the confirmation screen without round-tripping sensitive data through the browser — Redis was added for this. This is additive, not a divergence from any stated NFR.

No other deviations. The one-time reference code checksum approach, the stateless-portal decision, and the EOS-as-system-of-record boundary were all built exactly as agreed.

## Acceptance criteria

- A provider can complete the full happy-path flow (auth → reference code → confirm identity → upload → confirmation screen) in under 2 minutes on a standard broadband connection. Verified in UAT, 2026-08-12.
- Reference codes with an invalid checksum digit are rejected with the generic mismatch message, not a distinguishing error. Verified by unit test `intake-api/test/reference-codes.test.js`.
- Files that pass the `Content-Type` header check but fail magic-byte sniffing are rejected with 422 and never reach S3. Verified by unit test `intake-api/test/file-validation.test.js`.
- Files over 10MB are rejected with 413 before upload completes (not after a partial upload times out). Verified manually with a 12MB test PDF, 2026-08-13.
- No client-identifying data beyond masked name/DOB ever appears in Provider Portal logs. Verified by log review during UAT sign-off, 2026-08-14 — CloudWatch log group `provider-portal-prod` sampled and confirmed clean.
- EOS case owners can see an attached certificate document within 1 minute of a successful submission, via EOS's existing case view (no new EOS UI was built). Verified in UAT against a real EOS UAT case, 2026-08-14.

All criteria above were signed off by the Provider Portal delivery lead and the EOS product owner prior to Operational Handover.

## Operational notes

The `eos-sync` job (existing, extended for this feature) occasionally lags up to 10 minutes under EOS's own end-of-day batch load — a reference code created in that window may 404 for up to 10 minutes before it's usable. This is a pre-existing characteristic of `eos-sync`, not something introduced by this build; support should not treat a slow-to-appear code as a Provider Portal defect. If a provider reports this, check the `eos-sync` job's last-run timestamp in its own CloudWatch dashboard before escalating.

The Redis session store has no automated failover; a node restart mid-session forces the provider to re-authenticate and re-enter the reference code. This has not occurred in production to date but is a known gap, not yet raised as a formal risk with Architecture.
