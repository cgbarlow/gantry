# A workspace can be shared by its deployment

`docs/adr/0038-per-workspace-pat-no-global-credential.md` made a credential the property of one workspace and held it only in the architect's browser, forwarded per request. `docs/adr/0046-boot-time-bootstrap-pats-amend-adr-0038.md` carved out one narrow exception — a boot-time, startup-only, discovery-only credential — and closed by naming exactly the decision this ADR now makes: "A future ticket that wants this credential to do more than discovery (e.g. rendering rows server-side for a truly anonymous dashboard) is a new decision, not a natural extension of this one."

The gap that forces it. `lib/registry.js`'s `buildGitHubRow` (and its Azure DevOps, GitLab and Atlassian twins) opens with `if (!pat) return null`, then reads the instance's own `instance.yaml` out of the repo to build the row. Nothing is materialised server-side: every dashboard load re-derives every Provider-backed row from the Provider, live, with the credential on that request. Two consequences follow, and both are structural rather than incidental.

First, **the dashboard is not a shared artefact**. Two people hitting the same deployment with different PATs see different instance lists, because the view is a function of the viewer's token scope rather than of the deployment. Second, **a deployment can show nothing at all to a visitor who has not brought a credential**. For `#109`'s hosted demo that is fatal in a way `GANTRY_BOOTSTRAP_WORKSPACES` and `GANTRY_BOOTSTRAP_PATS` together cannot fix: they restore the *registry* — which workspaces and which instance slugs exist — but the rows are still built per request, so a visitor with no PAT sees an empty screen no matter how correctly the deployment is configured. That failure is also silent: the listing returns `200` with unreadable rows quietly omitted (each row builder's own "omit one row rather than fail the listing" contract), so nothing returns `authentication_required` and the browser's PAT prompt never fires.

There is also a modelling error underneath it. One credential is doing two unrelated jobs: **reading the repo to render the view** — which is a property of the deployment, since every viewer wants the same answer — and **writing on someone's behalf** — which is necessarily a property of the person. `docs/adr/0038` reasoned about the second and applied its conclusion to both. Its stated problem, verbatim, was that "the global default is precisely the mechanism that sends an Azure DevOps PAT to GitHub and produces a 401 nobody can explain" — an argument for *per-workspace scoping*, not for *browser-held-only*. Those were two decisions bundled into one, and the cross-provider-leak rationale only carries the first.

What genuinely is load-bearing about browser-held credentials is something `docs/adr/0038` never states, because at the time it did not need to: **Gantry has no authentication of its own.** There is no session, no login, no cookie, no user record — `lib/credential.js`'s `getCredential(req)` is a Basic-auth header decode and that is the whole story. So the viewer's PAT is not merely *a* credential; it *is* Gantry's authorization layer. "May you see this workspace?" is answered today by "can your token read that repo?", enforced by the Provider and never reimplemented here. That is the real cost of serving reads from a server-held credential, and it must be paid deliberately: from the moment a deployment reads a workspace on its own behalf, **everyone who can reach that deployment can read that workspace**.

Finally, the asymmetry that shows the current split is arbitrary. A server-directory workspace (`docs/adr/0031`) and a Provider-backed workspace fill the identical role — a collection of `instance.yaml` files the server renders rows from — yet `buildLocalRow` reads the server's own disk with no credential and is visible to every anonymous visitor, while `buildGitHubRow` reads a repo with the viewer's credential and is invisible without one. Same role, opposite trust models, and the only difference is where the bytes live. There is no principled reason the storage medium should decide who may look; that should be an operator's decision, stated once, per workspace.

## Decision

**A workspace may be *shared* by the deployment that serves it.** Sharing is declared by the operator, per workspace, and never inferred.

`GANTRY_BOOTSTRAP_PATS` is **renamed to `GANTRY_SHARED_WORKSPACE_PATS`**, keeping `docs/adr/0046`'s shape and fail-loud validation (a JSON object mapping workspace id to PAT, unset or blank meaning `{}` and nothing running). The rename is not cosmetic: the variable's meaning widens from "discover this workspace's instances at boot" to "this is the credential this deployment reads this workspace with, and therefore anyone who can reach this deployment can browse it." That consequence is security-relevant, so the name has to carry it — an operator must not be able to publish a private workspace by setting something that reads like a startup detail. The old name is **not** kept as an alias; it would leave the misleading name in circulation for exactly the setting where the misreading is most costly.

**Reading a shared workspace requires no credential.** When a request carries no PAT for a shared workspace, its reads resolve that workspace's shared credential instead. This covers the whole read surface — the dashboard listing, opening an instance, stage and module content, rendered artefacts, assets — not the listing alone. A listing that anonymous visitors can see but not click through is a worse outcome than showing nothing, because it converts an obvious failure into an invitation that dead-ends.

**Writing always uses the viewer's own credential, never the shared one.** Every mutation — commits, pull requests, work-item sync, assignee, stage advance, publish — resolves the requesting person's PAT or does not proceed. This is the line that keeps attribution honest and caps a leaked shared credential's blast radius at "someone read a repo", never "someone wrote to it as the deployment".

**A viewer who cannot write sees a read-only interface, not a failing one.** Editing affordances are off, with a stated reason and an action to add a credential. Whether someone can write is established by an explicit check at the moment a PAT is entered, and remembered — not inferred from the mere presence of a token. A personal Provider token that happens to be in the browser is common and grants nothing on someone else's repo; treating "has a credential" as "may edit" would re-create the dead end this decision exists to remove, one step later and after the work is lost.

**Every registered workspace is visible on the dashboard**, including one whose contents cannot currently be read and one that has no instances yet. `GET /api/workspaces` already needs no credential (`docs/adr/0038`'s own consequence, and the reason the browser can run its legacy-PAT migration uncredentialed at boot), so the set of workspaces is always knowable even when their contents are not. An unreadable workspace states that it is unreadable and carries the action that fixes it. This is what makes a credential reachable at all for a workspace with no instances in it: before this, Workspace Settings resolved only from an instance slug, so a registered workspace with nothing discovered inside it had no route to its own PAT field — the credential you needed to discover instances was only reachable through an instance.

**Shared reads are cached, and the cache is kept honest by change detection rather than by a clock.** Gantry updates its own copy directly when it makes a change, so an architect's own edits are visible immediately. Anything changed outside Gantry is caught by a conditional freshness check against the Provider — cheap, and free against Provider rate limits when it reports no change — so content is re-read only when the underlying ref has actually moved. There is no TTL and no staleness window to explain, and therefore no manual refresh control to add. **Only content read with a workspace's shared credential is ever cached**; anything read with an individual's PAT is never cached and never served to another request, since doing so would let one person's access silently widen another's.

## Alternatives considered and rejected

- **Give Gantry its own identity and per-user permissions.** The other coherent answer, and rejected as a different product: user records, sessions, invitations, roles, recovery, and a re-implementation of permissions the Provider already enforces correctly. Per-workspace operator-declared sharing reaches essentially the same usable outcome, because the operator setting the variable *is* the authorization decision. Nothing here forecloses adding identity later; doing it first would stall everything else.
- **Share the listing only, and keep instance content per-viewer.** Materially smaller — row builders alone — and it leaks only slug and stage metadata. Rejected: a visitor who can see a list but cannot open anything in it has been shown a shop window, and the credential prompt they hit on click-through is one they usually cannot satisfy. The demo this exists to fix would still not demonstrate anything.
- **A separate "public" flag, required in addition to a shared credential.** Safer by construction — a credential alone would never imply publication — and rejected as a second thing to get right for a property the first already states. A deployment-level credential for a workspace has no purpose other than serving that workspace to that deployment's visitors; splitting the statement in two invites the half-configured state where one is set and the other is not. The rename above is what carries the warning instead.
- **Keep reads viewer-credentialed and solve only the reachability and silence problems.** Honest, preserves `docs/adr/0038` intact, and genuinely fixes the "no way to enter a PAT" defect. Rejected because it leaves the deployment unable to show anything to anyone who has not first obtained a Provider token, which is the actual product failure — the reachability defect is a symptom several layers downstream of it.
- **A time-based cache (a TTL of a minute or so).** Rejected: the staleness window lands precisely on the case that matters most, an architect demonstrating Gantry live and waiting for their own change to appear, and it buys nothing that write-through plus a conditional freshness check does not buy without the wait. It would also require a manual refresh control to exist purely to work around itself.
- **A webhook from the Provider, invalidating the cache on push.** Genuinely better for changes made outside Gantry, and deliberately deferred rather than rejected: it requires a webhook and a shared secret configured on every workspace repo, which is real setup an operator must get right, for a marginal gain over a freshness check that costs nothing and needs no configuration. It remains available as a later optimisation.
- **Keeping `GANTRY_BOOTSTRAP_PATS` as an accepted alias.** Rejected: one setting with two names, indefinitely, with the misleading one still in circulation — to spare exactly one deployment a single configuration change.

## Consequences

- **`docs/adr/0038`'s "no server-side credential, ever" no longer holds for reads.** It continues to hold in full for writes: there is still no ambient credential, no global default, and no fallback for any mutation. This ADR supersedes `docs/adr/0046`, whose startup-only, discovery-only exception is subsumed by the broader read-time one decided here.
- **Anything in a shared workspace is readable by anyone who can reach the deployment**, including by script against the API. This is the trade being made knowingly, and it is why sharing is per workspace and declared rather than default. A deployment that sets nothing is unchanged: reads stay viewer-credentialed exactly as they are today.
- **The dashboard becomes a shared artefact.** Two viewers of a shared workspace see the same thing, which they do not today. For an unshared workspace the per-viewer behaviour is unchanged.
- **A credential's two jobs are now distinguishable in the code.** Any read path must be able to resolve either a shared or a request credential; any write path must resolve only a request credential. A path that cannot say which kind it is has a bug rather than a default.
- **The dashboard stops failing silently.** A workspace that cannot be read says so, in place, with its own fix — replacing an omitted row that was indistinguishable from an empty workspace, a misconfigured one, and one that does not exist.
- **Operators must update one Render value** when upgrading, and a deployment that does not is unshared rather than broken: an unset `GANTRY_SHARED_WORKSPACE_PATS` is the same no-op an unset `GANTRY_BOOTSTRAP_PATS` was.
- **Provider read traffic stops scaling with viewers.** It scales with change instead, which is what makes anonymous browsing affordable at all — and is a prerequisite rather than an optimisation, given `#106`'s existing report of the demo dropping connections under concurrency.

Status: accepted, superseding `docs/adr/0046-boot-time-bootstrap-pats-amend-adr-0038.md` and amending `docs/adr/0038-per-workspace-pat-no-global-credential.md` (whose per-workspace scoping, and whose no-fallback rule for every *write*, both still hold). Decided during the shared-workspaces grilling session, 2026-09-22, ahead of implementation.
