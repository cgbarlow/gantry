# Comment/prose text: one paragraph per line, not hard-wrapped at a fixed column

An audit for #117 found this repo's own comment and documentation prose inconsistently hard-wrapped: `CONTEXT.md` and the earliest ADRs (`0001`-`0006`) wrap at ~80 columns, the next few ADRs (`0007`-`0009`) wrap wider at ~100, and every `//` and JSDoc comment block across `lib/`, `web/` and `tests/` still wrapped at ~80 — while `README.md`, `CLAUDE.md`, `docs/agents/*.md` and `exec-summary.md` already write each paragraph as a single line, relying on the editor to soft-wrap it for display. Markdown makes the hard-wrapped style pure overhead: CommonMark collapses consecutive non-blank lines within one paragraph into a single rendered line regardless of the source's own line breaks (used throughout `CONTEXT.md`'s glossary entries already, each really one paragraph split across a term line, a description, and an `_Avoid_` line with no blank line between them), so the two styles render identically — the hard-wrapped source only cost every future edit a full-paragraph reflow, and a noisy diff, for no reader-visible benefit.

We reflowed every hard-wrapped comment/prose paragraph — in code comments (`//` and JSDoc `/** */` blocks) across `lib/`, `web/`, `bin/` and `tests/`, and in `CONTEXT.md` and `docs/adr/0001`-`0009` — to one line per paragraph, and adopt that as this repo's going-forward convention for its own comment/prose text: write a paragraph as a single line; don't hard-wrap it at any fixed column. A bullet list item or a JSDoc `@tag` keeps its own line but likewise shouldn't hard-wrap its own text across further lines — its wrapped continuation joins back onto that one line, same as a plain paragraph's. Rely on the editor's (or the code-review tool's) own soft-wrap to display a long line, not on the source's line breaks.

This covers this repo's own authored comments and internal documentation — code comments, `CONTEXT.md`, `docs/adr/`, `docs/agents/`. It deliberately does not reach `instances/*/modules/*.md`: that's business content mirroring a real Contoso/architect-authored artefact, not engineering documentation, and stays however its own author wrote it. Nor does it reach `reference/`, which holds externally-sourced material kept verbatim.

Alternatives considered and rejected:

- **Pick a wider fixed wrap column (100, matching `docs/adr/0007`-`0009`) instead of no column at all.** Rejected: still costs a full-paragraph reflow (and diff noise) on every edit, for a rendering difference that never actually shows up to a reader — Markdown collapses either style identically, so the choice of column only ever affects the raw source.
- **Leave the existing inconsistency as-is, only asking new text to stop wrapping at ~80.** Rejected: the current three-way split (`~80` / `~100` / unwrapped) already reads as unintentional drift rather than a real distinction between kinds of file, and leaving old files as they were keeps that same confusion for anyone diffing across them later.

Status: accepted.
