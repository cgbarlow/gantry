# A narrow, opt-in exception to "no server-side credential"

`#111` (`GANTRY_BOOTSTRAP_WORKSPACES`) and `#112` (Provider-backed instance discovery on the request's own credential) together mean a Provider-backed workspace, once redeclared, gets its instances back the moment a real, authenticated request arrives — the registry itself is derived state, rebuilt on every boot, and the first request carrying a usable Workspace PAT triggers `lib/instanceRegistry.js`'s `backfillProviderInstances` to list `gantry-workspace/` in that workspace's repo and register what it finds. `#112`'s own doc comment is explicit about the shape of what's left: "on the request-credential path, a restored workspace's instances reappear on the first authenticated request, not at boot."

For an operator restarting a deployment they themselves are about to use, that gap is invisible — they restart, log in, the dashboard populates. For an unattended deployment — the hosted demo above all — there is no "they restart and log in" step. A container comes back up, `GANTRY_BOOTSTRAP_WORKSPACES` redeclares the workspace, and the dashboard is reachable immediately — showing a workspace with zero instances in it, indistinguishable from a workspace that was never populated in the first place, until whoever happens by next supplies a PAT. For a demo meant to look "restored," that reads as "still broken."

Closing that gap means running discovery before any request exists to carry a credential at all — which means the credential itself has to come from somewhere other than a request. `docs/adr/0038-per-workspace-pat-no-global-credential.md` is exactly the decision that ruled that out: "The global-default credential tier is removed. Every workspace holds its own PAT; there is no fallback," held only in the architect's own browser and forwarded per request, with the server holding nothing. A boot-time PAT map is precisely the kind of server-held credential that decision exists to prevent, so it cannot be introduced as an incidental side effect of a persistence fix — it has to be adopted on purpose, scoped as narrowly as the problem allows, and recorded here.

## Decision

`GANTRY_BOOTSTRAP_PATS` is a new, **opt-in, off-by-default** environment variable: a JSON object mapping workspace id to PAT, `{"<workspaceId>": "<pat>", ...}` — the same shape, and the same fail-loud validation style, as `GANTRY_WORKSPACE_PATS` (`docs/adr/0043-mcp-server-is-a-separate-render-hosted-http-client.md`'s own boot-time credential map for the separate MCP server process). `lib/workspaceBootstrap.js`'s `parseBootstrapPats` parses and validates it; unset or blank, it returns `{}` and nothing below it runs — zero behavior change for every deployment that doesn't set it, which is every deployment today.

When set, `lib/server.js`'s boot sequence — right after `#111`'s `applyBootstrapWorkspaces` registers each `GANTRY_BOOTSTRAP_WORKSPACES` declaration — calls `lib/workspaceBootstrap.js`'s `discoverBootstrapPatInstances` for the subset of just-registered workspaces that have a matching `GANTRY_BOOTSTRAP_PATS` entry. That function runs `#112`'s own `backfillProviderInstances`, one call per matched workspace, each scoped to that workspace's id alone (`backfillProviderInstances`'s new `options.workspaceId`) — never the whole registry with one PAT tried against everything undiscovered, which is what the existing request-credential path does and is fine there (a request's PAT and the workspace it's scoped to are the same thing by construction) but would not be fine here, where a boot-time map can plausibly hold several different workspaces' credentials at once. Scoping each call to its own workspace id keeps this credential's blast radius identical to the browser's own: one PAT, one workspace, never tried against another.

This runs fire-and-forget, the same posture `lib/server.js`'s existing startup library-repo refresh already established for "resolve a boot-time credential, run something at startup, degrade gracefully if it fails": never awaited before the server starts listening, so a slow or unreachable Provider host never delays startup. A rejected, expired, or simply wrong boot PAT is caught and logged by workspace id — never by PAT — and that workspace is left exactly where `#112` alone would have left it: undiscovered until a real request supplies a working credential. Nothing about a bad boot PAT fails startup, and nothing about it prevents the request-credential path from working normally afterward.

Because a Provider-backed row still needs a per-request credential to actually read the repo's content (`lib/registry.js`'s `buildGitHubRow`/`buildAzureDevOpsRow` return `null` with no `pat`, registered or not), boot-time discovery does not mean `GET /api/instances` shows real rows to a request with no credential at all — an anonymous visitor still sees nothing, before and after this ticket. What it buys is narrower and still real: the *registry* is warm before anyone arrives, so the first authenticated request — the architect's first real load, or the MCP server's first call against a workspace it already holds a `GANTRY_WORKSPACE_PATS` entry for — gets its row back without itself paying `#112`'s discovery round trip, and an unattended dashboard that happens to be viewed by someone who already has a PAT in their browser (the common shape for a returning demo visitor, or any automated health check hitting the API with a credential) sees populated instances immediately rather than after one extra "discover, then render" request.

## Alternatives considered and rejected

- **Do nothing — leave `#112`'s request-credential path as the only trigger.** Rejected: this is precisely the gap the ticket exists to close. It is a real, working answer for an operator who logs in after every restart; it is not one for an unattended deployment nobody logs into right after it comes back up.
- **Give the server an ambient/global PAT, the way `GANTRY_LIBRARY_PAT_*` already does for library repos.** Rejected outright: a Library repo's server-side credential (`docs/adr/0036`, §Credential) exists because a library repo is content the *server* reads on its own behalf, not a workspace an architect owns — conflating the two would resurrect exactly the cross-provider, cross-workspace leak `docs/adr/0038` removed. `GANTRY_BOOTSTRAP_PATS` is a map, not a scalar, and every entry stays pinned to one workspace id for exactly that reason.
- **Have the server render rows without a credential for a boot-discovered workspace** (treat boot-time discovery as license to also read repo content server-side). Rejected: that would need the server to hold the PAT indefinitely and use it on every subsequent render, not just once at boot — a materially larger credential lifetime and blast radius than "run discovery once, at startup, then forget it," and not what this ticket's own scope (discovery only) asked for.
- **Let one boot PAT stand in for every undiscovered workspace**, the same breadth `#112`'s single request-credential already has. Rejected: a request's PAT is inherently scoped to the one workspace the browser sent it for, so trying it against every other undiscovered workspace in the same registry costs nothing extra in practice (it just fails those repo). A boot-time map can hold several *different* workspaces' credentials in one process; trying workspace A's PAT against workspace B's repo — even only until B fails to accept it — is exactly the cross-workspace credential use `docs/adr/0038` exists to prevent, so each `backfillProviderInstances` call here is scoped to its own workspace id.
- **A TTL or periodic re-run of boot-time discovery**, mirroring nothing in particular but "just in case." Rejected: discovery only ever has anything to do for a workspace with zero registered instances (`#112`'s own contract); once discovered, re-running buys nothing and this ticket introduces no polling of any kind, consistent with the Library-repo refresh's own "no polling, no TTL" precedent it's modeled on.

## Consequences

- A deployment that sets `GANTRY_BOOTSTRAP_PATS` is knowingly trading a piece of `docs/adr/0038`'s guarantee — "no server-side credential, ever" — for "instances visible sooner, to whoever arrives with a real credential of their own." That trade is opt-in per deployment, not a default, and this ADR is what makes the trade a decision rather than a surprise.
- This credential's lifetime is startup only: read from the environment once, used for at most one discovery pass per matched workspace, then never touched again by this code path. It is not cached, not refreshed, and not consulted by anything else — a request still authenticates exactly the way `docs/adr/0038` describes, with its own carried PAT.
- Operators of a deployment that does *not* set it see zero change: parsing an unset `GANTRY_BOOTSTRAP_PATS` costs one cheap no-op check, and `#112`'s request-credential path remains the only thing that ever runs.
- A future ticket that wants this credential to do more than discovery (e.g. rendering rows server-side for a truly anonymous dashboard) is a new decision, not a natural extension of this one — see "Alternatives considered and rejected" above for why that's deliberately out of scope here.
